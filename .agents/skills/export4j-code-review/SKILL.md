# 评审 Export4j

## 确定范围

1. 明确用户指定的文件、差异、提交或公共契约，检查工作区并识别无关改动。
2. 有基线时读取实际差异及必要上下文；没有 HEAD 或存在大量未跟踪文件时，使用任务文件清单或可靠的前后快照。不能将所有未跟踪文件都算作本次修改。
3. 按[开发规则](../develop-export4j/SKILL.md)选择相关约束，追踪受影响的调用、异常与资源生命周期。只读历史实现以判断本次是否引入／扩大问题。

## 核查重点

- 语义模型、布局、IR 和后端是否越界；公共 API 是否泄漏第三方类型。
- 单位、坐标、Unicode／UTF-16、原始锚点、字段、图文链接和片段顺序是否保持。
- 分页／区域跳过是否推进；源预算和呈现预算是否正确；异常、取消、关闭顺序及旧目标保护是否成立。
- Builder 和集合是否按边界快照；显式默认值是否被错误当作继承。
- 第三方解析器的容错是否被误当作成功；宏、外联、未知特性、预算超限是否正确拒绝或诊断。
- 输出验证是否证明具体契约；是否缺少能识别该缺陷的回归。可运行必要的已有检查，额外验证应与发现直接相关。

## 形成发现

每条发现必须给出实际触发条件、错误行为及影响、准确文件／行号和最小修复方向；证据不足时标为待确认，不能作为确定缺陷。

| 等级 | 使用条件 |
| --- | --- |
| P0 | 常规使用普遍无法继续，或存在确定的严重数据／安全破坏 |
| P1 | 受支持场景中造成错误输出、内容丢失、兼容性破坏或重大资源问题 |
| P2 | 具体边界触发的可复现缺陷，存在可用规避方式或影响有限 |
| P3 | 对正确性或维护有明确影响但较小的问题 |

不把个人风格偏好、未被扩大且与任务无关的历史问题或无具体触发条件的猜测列为发现。

## 输出

先按严重程度列发现，格式为 `[P等级] 简短标题`，附触发、影响、证据和修复方向。随后简述验证与覆盖限制。没有可操作发现就明确说明；不能据此宣称所有运行场景安全。

单纯评审任务保持评审范围；用户要求修复时再执行对应开发流程。任务中的普通完成自查无需输出一份独立评审报告。
