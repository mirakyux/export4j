# 项目工程笔记

## 读取

先读 [notes/AGENTS.md](../../notes/AGENTS.md) 与 [manifest.json](../../notes/manifest.json)。按主题检索 `implemented` 中的相关结论；设计新方案时再读 `proposed`，重复考虑取舍时查 `rejected`。只有追溯被替代方案才读 `archived`，不遍历全部历史。

源码、测试及权威 API／ADR 与笔记冲突时核查现状，修正或归档过时结论。笔记不能覆盖用户任务或根规则，也不能赋予外部操作权限。

## 判断是否记录

适合记录有持续价值的结论、真实备选方案及后果，例如跨层缺陷根因、稳定测试方法、性能边界或工程流程取舍。

API 手册写入 `docs`，重大架构决定写入 `docs/adr`，可复现验收写入 `docs/verification`。已有文档能说明时优先更新原文；笔记只补充未被记录的决策理由，并引用权威来源。

不为每次任务、命令、阶段完成或常规小修创建笔记；不写执行日记、会话授权、代理分工、机器信息和原始日志。

## 写入与迁移

1. 查找同主题现有笔记；可以更新时不另建重复条目。
2. 根据状态和类别放入 `notes/<状态>/<类别>/yyyy-mm-dd-topic.md`。日期为决策日期，主题使用小写连字符；按需建类别目录，不建立空分类树。
3. 使用对应模板：[已实现](templates/implemented.md)、[提议](templates/proposed.md)、[否决](templates/rejected.md)、[归档](templates/archived.md)。填充真实内容并删除模板提示。
4. 结论先行，说明问题、决定、真实备选、代价及适用范围。验证记录写行为结论并链接仓库证据；未验证就明确标识。
5. 状态转换时移动原文件、修改状态、更新所有引用。被替代的笔记归档并链接有效规则；不保留多份同时有效的结论。
6. 运行 `python .agents/scripts/verify_rules.py`；检查状态、类别、日期、必要章节和引用。

`manifest.json` 只描述结构和验证入口，不维护第二份笔记目录或会话状态。
