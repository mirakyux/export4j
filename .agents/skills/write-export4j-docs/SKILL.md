# 维护项目文档

## 确定事实与归属

- 先核对相关源码、测试、示例及当前契约。目标写入立项／路线图，真实支持状态写入[支持矩阵](../../../docs/capabilities-api.md)与[能力缺口表](../../../docs/capability-gaps.md)，不得把规划写成已实现。
- API、单位、坐标、空值、异常、资源所有权及兼容性写入 Javadoc 和对应 `docs/*-api.md`。
- 重大架构取舍使用 [docs/adr](../../../docs/adr) 的现有序号和结构；其他长期工程取舍按 [agent-notes](../agent-notes/SKILL.md)记录，不复制同一决定。
- 验收结论写入 `docs/verification`，区分实现、自动检查、独立工具、视觉／阅读器验证及正式发布。

## 内容与表达

- 使用项目名称 Export4j、包／group `com.mirakyux.export4j` 和模块前缀 `export4j-*`。README 保留中英文副标题；不新增无实际用途的命名沿革或同步说明。
- 中文先说具体行为，再说使用条件和限制。使用有层次的标题、标准 Markdown 表格、完整代码示例及仓库相对链接。
- 命令从仓库根目录运行，注明 Windows 与 Linux/macOS 的 Wrapper 差异；先核实任务、参数和资源真实存在。
- 路径写仓库相对位置，必要配置用含义明确的占位符。不得包含个人路径、机器标识、凭据、会话授权、代理分工或原始日志。
- 验证环境只保留影响复现的工具版本及通用平台条件；临时输出、失败堆栈和私有样本放忽略目录，不复制进公共文档。
- 不夸大范围：有限样例不证明通用 Word 往返、完整 OpenType、PDF/UA、通用阅读器兼容、恶意输入沙箱或长期无泄漏。

## 校验

1. 检查修改的链接、标题、示例和实际文件；更新受影响索引，删除失效的重复说法。
2. 纯文档修改无需增加 Java 测试；出现可执行示例或公共契约变化时，按对应开发和输出规则验证。
3. 修改 `.agents` 或根 `AGENTS.md` 后执行 `python .agents/scripts/verify_rules.py`。
4. 交付前核对 Git 候选文件；忽略规则不能隐藏已经被跟踪的敏感文件。只报告实际完成的检查范围。
