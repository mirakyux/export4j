# 工程笔记：共享项目规约的组织与维护

状态：已实现

## 先说结论

根 `AGENTS.md` 负责规则优先级、共同边界与任务导航；`.agents/skills` 按工作类型保存步骤和技术细则。两者均属于可随项目共享的内容。

## 问题

文档引擎涉及模型、字体、分页、语义来源和多输出格式。把所有细则放入单一入口，会增加定位成本，并使能力状态、工程规则和验收证据混杂。

## 决策

使用[根入口](../../../../AGENTS.md)和[技能导航](../../../README.md)按需读取规则。保留细化的引擎不变量及功能验证矩阵，架构决定继续以 [docs/adr](../../../../docs/adr) 为权威，笔记只补充未被其他文档覆盖的长期取舍。

共享文件仅记录项目内容，采用仓库相对引用。机器路径、凭据、会话状态和原始日志不属于共享规约。

## 考虑过的备选方案

- 所有规则放在根文件：入口过长，难以按任务选择相关约束。
- 将整个 `.agents` 忽略：协作者无法复用项目规则，也不利于评审规则变化。
- 在笔记中复制 API 和 ADR：会产生多份容易冲突的事实源。

## 后果

规则可随项目协作与评审；开发者需要同步契约及其引用。笔记按状态和类别组织，按需创建，不维护执行日记或空功能规划。

## 验证

[规则检查器](../../../scripts/verify_rules.py)检查技能、链接、笔记状态及常见机器路径／凭据模式。它只验证明确的结构和模式，不能代替人工事实核查或全部仓库的敏感信息审查。

## 适用范围

适用于项目 Agent 工作规约、长期工程笔记及其维护。公共 API 仍以源码、Javadoc 与对应指南为准；构建、输出和发布验证仍按各自契约执行。
