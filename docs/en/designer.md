# HTML Template Designer

`export4j-designer` is an optional standalone local application for editing existing XML templates and resource ZIPs through an HTML interface. It calls the existing Java engine for data binding, pagination, preview and export; the core library does not depend on the designer. The application is excluded from Maven library releases, the BOM and the library API baseline.

## Starting the Application

Building from source requires JDK 21, Node.js 22 or later, and npm. Gradle installs and bundles the frontend according to the lockfile. Run from the repository root:

```powershell
.\gradlew.bat :export4j-designer:run
```

On Linux/macOS, use `./gradlew` instead. After startup, open the local address shown in the terminal; the default is `http://127.0.0.1:8784/`. Change the port with `--args="--port=8785"`; `--port=0` selects an available port.

You can also build an installation directory first, then run its launch script:

```powershell
.\gradlew.bat :export4j-designer:installDist :export4j-designer:distZip
.\export4j-designer\build\install\export4j-designer\bin\export4j-designer.bat
```

The installation contains the application, bundled frontend, runtime dependencies, explicit sample fonts and licenses; it does not include a JRE. Running the distribution requires no Node.js. Generation and conversion do not call print services, printer drivers, Office or browser layout engines. The browser displays the editing interface and Java-engine preview.

## Convenient Editing and Precise Layout

“Independent text-and-image grid” first opens a visual layout picker: full width, two equal cells, three equal cells, wide left/narrow right, or narrow left/wide right. Insertion selects the first cell. Double-click its body or select “Edit inner content” in the inspector to start writing. New cells contain empty paragraphs without sample text. Each cell lays out independently; content does not flow between cells, row height follows content, and the whole row paginates together. Use “Body columns” when continuous body text should flow automatically between columns.

Existing content can become a side-by-side layout directly: select adjacent direct-child paragraphs or tables under the same document/section, insert “Independent text-and-image grid” and keep “Place selected content side by side” checked. Original content moves into cells in reading order, preserving text, images, tables and IDs without copying and reentering it. Excess content is appended to the final cell in order; cells without content stay empty. Ineligible selections show the specific reason. A single selection supplies only the insertion position and does not implicitly move body content.

When a cell is selected, the inspector combines inner-content editing, insertion and layout actions. The layout area shows the current cell width and provides splitting, merging with the right cell and adding rows; “Row layout” opens the same visual picker. Dividers between neighboring cells appear within the current row. Dragging changes their proportions; when focused, Left/Right adjusts them one track at a time. “More” provides “Narrower/Wider” buttons. Drag a handle outside the cell boundary onto another cell to swap positions, or click “Swap backward/Swap forward”. Drags show proportions or target feedback and write back only on release; Esc cancels. Normal scrolling to another page still allows swapping cells within the same grid. A source, session or preview-geometry invalidation cancels the drag; an unsynchronized or failed preview prevents applying its result.

The inspector displays a proportion diagram for the current row; click it to select a cell. Layout adjustments remain in this inspector. Reducing the cell count appends existing content to the final retained cell in order, and the whole operation is undoable. Row numbers, start tracks, spans and spacing are grouped under “Advanced track settings”; ordinary authoring does not require them. Layout actions on item-level loops, conditions or fragments show their read-only reason and do not move content across scopes. Saved ZIPs retain grids, items and original child nodes. Sample 14 demonstrates partial column spans, offsets and body-column combinations. See the [grid guide](grid-layout-api.md) for syntax and boundaries.

“Body columns” supports one to three columns, pt gaps, width ratios and balancing. Paragraphs/tables inside columns can be edited directly on the canvas. Built-in two- and three-column samples include full-width tables and images before resuming columns with the same settings. After selecting a direct-child paragraph of a column flow, “More actions” in the inspector offers “Insert full-width table/image”. During editing, “Full-width table/image at cursor” splits the paragraph at the current caret, preserves surrounding body text and inline formatting, and resumes the same column settings. Complete dynamic nodes can serve as boundaries between blocks; children inside loops/conditions cannot be extracted from their scope. See the [body-column guide](column-flow-api.md) for syntax, saving and cross-format restrictions.

Switch modes above the canvas at any time. Both modes share XML, test data, resources and undo history; they do not create separate templates.

| Mode | Purpose | Display and refresh |
| --- | --- | --- |
| Convenient editing (default) | Write body text, select text and adjust styles | The browser immediately displays original template text and variable markers. Active typing does not request the backend on every keystroke; completing an edit validates it and updates pagination. Font positions and line breaks are approximate |
| Precise layout | Check final line breaks, pagination and output | The Java engine binds test data and lays out the document. Text drafts update the preview after a short debounce, retaining the editor and caret |

Click to select on the canvas; double-click a paragraph, heading, list item or inline cell to type in place. A selected single text element also accepts Enter/F2. Adjacent ordinary paragraphs and headings on the same page and in the same body area use a continuous text-editing region. Adjacent paragraphs in the same block cell, grid item or body-column region also support continuous editing. Move the caret and select across paragraphs; Backspace at a paragraph start or Delete at its end merges paragraphs without joining content across cells or loop scopes. Enter splits a paragraph; a paragraph split from a heading uses ordinary body formatting. Shift+Enter inserts a line break; Ctrl+Enter finishes editing. Inline cells, list items and fixed boxes edit separately; Enter in inline cells and fixed boxes inserts a line break. See [Editing Inside Containers](#editing-inside-containers) for cell navigation and continued editing.

Selecting text displays a floating formatting toolbar near the selection with bold, underline, strikethrough, color and font size; collapsing the selection hides it. Variables, images and page-number fields remain structural objects. Cross-paragraph editing preserves unchanged paragraph properties and mixed formatting. Undo within the editor handles the current text input; after completion, workspace undo restores committed changes. Single-paragraph headers/footers also support double-click body editing; complex regions retain structure-tree and XML entry points.

When a paragraph spans multiple pages, the editor displays “Paragraph spans pages · Edit complete source text”. Changes apply to the entire source paragraph. Use the keyboard to locate text; precise caret restoration from a page fragment is not currently provided.

The top “Insert” menu groups entries into “Text”, “Layout and containers” and “Pagination and references”. Selecting a component exposes “Insert before” and “Insert after” beside its frame; these open a canvas menu grouped into “Text”, “Layout and containers” and “Pagination”. Both “Layout and containers” groups offer tables, data lists, data tables, body columns and independent text-and-image grids. Data controls open an array-binding dialog; grids open the layout picker. A new paragraph or heading immediately enters text editing; typing replaces its default text. “Component actions” provides duplication, reordering and deletion. Esc closes the menu. The canvas menu supports arrow keys, Home/End and Enter.

Drag on blank space to select a rectangle; Ctrl/Shift supports multiple selection without switching between selection and text tools. After selecting a component, drag its handle directly or hold on its body for about 350 ms before dragging. Early release or movement exceeding 6 px before activation cancels the pending drag. A movement preview appears during dragging. In-flow components also show an insertion line and placeholder frame; fixed components show snap guides near alignment positions of other objects or the page. Esc or pointer cancellation abandons the operation. Results write back to XML only on release. Dragging always follows the component's own layout property and never automatically converts it to fixed positioning.

Insertion, order, position and size changes appear first in the canvas and properties, then the Java engine asynchronously calibrates the precise layout. While calibration is pending, selection, text editing, undo and structural commands such as “Move up/Move down” remain available. Dragging, resizing, rotation and arrow-key movement of fixed components depend on canvas geometry and require “Layout synchronized”. Source, test-data, resource or preview invalidation during an operation cancels it; normal scrolling to another page does not. Validation failure retains changes and displays the reason, allowing retry after correction. Template export first synchronizes the current valid source. Test export checks actual data and the chosen policy before generating the file.

The toolbar distinguishes “Calibrating layout”, “Layout validation failed”, “Layout update pending” and “Layout synchronized”. Synchronization is shown only after a successful preview matching the current template source, test data and resources. Preview failure retains the last valid canvas and displays the reason. Results from stale requests or old document sessions cannot mark the current draft successful.

Adding or replacing a resource first saves active text drafts. Body input briefly pauses during the resource write and resumes afterward, preventing a resource response from overwriting concurrent text. Ordinary layout calibration does not lock text editing.

In convenient editing, line breaks or larger text can increase the editor height. Subsequent body content on the same page temporarily moves downward while the footer stays fixed. This is immediate browser editing feedback. Completing the edit makes Java recompute actual line breaks, pagination and subsequent content positions.

“Layout mode” under “Position and size” is a component property:

| Layout mode | Dragging and keyboard actions | Body treatment |
| --- | --- | --- |
| In flow (default) | Dragging shows before/after insertion lines and changes source order; “Move component up/down” or Alt+↑/↓ is also available | Retains body space and lets surrounding content close gaps automatically; ordinary arrow keys do not convert it to fixed positioning |
| Fixed position | Free dragging; resizing from all frame edges and corners; pt coordinates/dimensions in the inspector; arrow keys move 1 pt and Shift+arrow moves 10 pt | “When body text meets it” chooses overlay or top/bottom avoidance; the rotation control is on the frame's right |

Top-level paragraphs, image paragraphs and tables can explicitly become fixed-position objects measured from the paper's top-left corner. Dynamic tables, lists, loops and condition containers reorder as whole units, retaining bindings, conditions and template structure. Cells still support double-click editing; an expanded data item cannot be mistaken for an independent source component. Multiple sibling in-flow components reorder as an ordered block; multiple fixed components translate together. Returning a fixed component to flow places it near body components according to its current page and vertical position.

“Overlay body” on a fixed component reserves no body space and allows overlaps, with layer order determining display order. “Top/bottom avoidance” retains body text above the object and continues below it when encountered. Avoidance spans the whole body width; side wrapping is not provided. This property is stored in the template's `body-flow`. Java-engine preview and PDF/SVG/PNG output share the same layout result.

An unrotated fixed table still supports single-click whole-table selection and double-click cell editing; merged cells use actual layout geometry. Rotated tables use properties or node XML for content editing. The canvas does not overlay unrotated cell editor boxes on them.

A fixed box can use fixed width or fill the remaining space to the right. Height can be fixed, grow with content or fill the remaining space below. Content exceeding the available page fails. Physical page `0` means every page; a positive number selects a document physical page. Missing target pages are added within the declaring section, subject to page-count budgets. Documents containing generated contents pages currently reject explicit physical-page selection and top/bottom avoidance. See the [overlay API (Chinese)](../page-overlays-api.md) and [architecture decision (Chinese)](../adr/0107-interactive-template-canvas.md).

When the canvas has focus, PNG/JPEG images can be pasted from the clipboard. Image bytes become template resources saved in the ZIP. Images retain the current container and data scope; pasting into an existing fixed box adds to its content. At every position, the Java engine measures actual available width/height for the new image paragraph before proportional scaling. A small existing image's hit width does not constrain the new image. Measurement includes header/footer reservations, footnotes, body-avoidance areas, paragraph spacing and keep-with-next chains. Fixed page regions, grid items and unsplittable table rows also reserve height needed by existing and subsequent content. Tables include padding and repeating headers; nested cells can use inner space left by taller neighboring cells. No available line space causes rejection before committing image resources. Resource and image paragraph commit together; undo/redo restores both. Any candidate-validation failure leaves neither a new resource nor partial source. Unsupported structural positions, header cells forbidding block content and conversion of inline cells with conditional styles are explicitly rejected. Images are not moved to the document end, and style rules are not discarded.

Fixed boxes and rotation are retained in PDF/SVG/PNG. When testing DOCX or other formats, unmappable positions and angles are still rejected, warned about or ignored according to the selected loss policy. Convenient editing does not change the actual capabilities of each format.

See [Phase 113 (Chinese)](../verification/phase-113-interactive-canvas.md) for evidence of both modes, direct canvas editing and independent outputs.

## Editing Inside Containers

After inserting a table, data list, data table or body-column region, the designer enters its first editable content: a table cell, data-list item template or inner body-column paragraph. Selecting the container again and double-clicking or pressing Enter/F2 enters its content. Double-clicking specific text or a cell edits that location without requiring step-by-step structure-tree navigation.

The inspector combines properties, body text, direct child content and container actions for the current node. Click child content to descend, and use the inspector's top breadcrumb to return to any ancestor. Use “Edit inner content” for in-place typing. Tables navigate by current cell, grids by independent item, and body columns by inner content. After double-clicking into a table or grid, clicking another cell in the same container continues editing there. Clicking outside or completing editing exits. In-place editing preserves container structure; inner changes do not become outer body content.

Inside a table's in-place editor, Tab/Shift+Tab moves to the next/previous cell in the actual source order of header and body cells. Merged cells visit only real anchor cells; data tables do not repeatedly traverse every expanded record. Cell navigation still works after selecting a variable marker. Navigation without input keeps the original source. Reaching the first/last boundary commits and exits without implicitly adding rows or data records. Adjacent paragraphs in block cells support continuous selection, splitting and merging. Enter in inline cells remains a line break; use “Add content → Text paragraph” to explicitly convert when multiple paragraphs are needed. Tab is not intercepted during Chinese input-method composition.

“Add content” in the inspector opens “Add inside container”, allowing text paragraphs, images or tables in the current cell, grid item or body-column region. Existing content remains. Adding block content to an inline cell first preserves original text and inline objects in a first paragraph, then appends the new content. An inline cell with `style-if` rules must have those rules explicitly removed before conversion; the designer explains the reason and does not silently discard them. Existing body-column and grid nesting restrictions still apply.

For ordinary tables, “Rows, columns and merges” in the inspector provides insertion above/below, insertion left/right, deletion of the current row/column and “Select cells and merge/split”. A second structural-action panel is not duplicated elsewhere. Actions share undo/redo. Adding a column updates both header and body, with at least one body row and one column retained; deleting body rows does not delete the header. Tables with merged cells also support safe row/column insertion and deletion: insertion through a merged range extends its span; deleting covered rows/columns reduces it. Deleting the first row of a vertical merge moves the retained anchor and content to the next row. If actually deleted nodes have external references, those references must be adjusted first. “Insert table” in the top and canvas menus uses the same default structure with real header and body rows.

Selecting a table or cell displays neighboring column dividers using the cell outer bounds supplied by the Java engine; padding is not guessed from text hit boxes. Dragging displays both column widths in pt and applies changes only on release. With a divider focused, Left/Right adjusts 1 pt, Shift+Left/Right adjusts 10 pt and Esc cancels a drag. Expand the current column's pt value in the inspector to enter a precise width directly. Adjustment affects the current and neighboring columns and saves explicit fixed pt widths; declarations for other columns remain. Handles and precise input are unavailable when geometry is uncertain because the preview is unsynchronized, the table is rotated, multiple instances occur on one page or insufficient cell boundaries are available. Column declarations remain configurable through properties/XML.

Selecting a direct-child paragraph/table within a cell, grid item or body-column region enables “Duplicate current paragraph/inner table” and “Delete current paragraph/inner table”, explicitly operating on inner content while retaining the outer container. Active text editing must finish before either command. Body columns and grid items retain at least one block; table cells can have block content cleared. Deleting externally referenced content is explicitly rejected.

When HTML-table clipboard data is pasted into a canvas body editor, clipboard plain text takes precedence. If only HTML is available, source rows/columns become Tab/newline-separated text, retaining paragraph breaks within cells. This writes into the current body text; it neither creates a table automatically nor distributes two-dimensional data across multiple target cells.

A data table's `rows` stores only one body-row template. Editing a cell in an expanded record changes that template, so all records use the new content. Template columns can be adjusted; the array still determines record count and order. A data list's `list` similarly stores only one item template, whose text, variables and formatting can be edited. Add actual items by changing the array rather than duplicating the unique item template.

When a bound array is empty, template structure and inner-content selection remain available. If no canvas object can be displayed, the editing entry opens the inspector and focuses the body editor, allowing direct template changes without adding fake array data. Load actual test data afterward to check layout. See [container-editing interaction verification (Chinese)](../verification/designer-container-ux.md), [editing-workflow completion verification (Chinese)](../verification/designer-workflow-closure.md) and [subsequent editing-workflow verification (Chinese)](../verification/designer-workflow-v2.md) for operations and restrictions.

## Template Logic and the Inspector

The inspector's top breadcrumb shows “Document → Container → Child structure → Current node”. Click a direct child in a document/container content list to view and edit it in the same inspector; click the breadcrumb to return upward. Conditions, loops, lists, tables and grids share this path, while the document structure tree retains the global overview. There is no separate logic sidebar or duplicate inner hierarchy in the canvas toolbar.

The canvas displays only the layout for current data. Unmatched condition branches and templates in empty arrays remain visible in inspector content lists. The condition inspector directly shows the field path, comparison, comparison value and current test value. Enter a path manually or expand field search to select a variable. Equality, inequality, magnitude comparisons, text containment and boolean checks are supported; numbers compare with exact decimal precision and no code executes. Changing a test value in existing root data automatically previews it without an update button. Continuous typing retains focus and caret; input-method composition previews after composition ends.

Click “Add condition branch” to configure `status = 1`, `status = 2`, then `status = 3`; the final “Other / other” is the fallback. Branches can use different fields and comparisons, are evaluated top to bottom, and display only the first match. Later branches can be deleted independently while retaining subsequent conditions and other, with undo support. The first branch must remain, but its condition and content can be changed directly. “Add nested condition” within a branch continues nesting, still using breadcrumbs in the same inspector.

Multiple branches save as the existing conditional chain of `if` nested inside `else`. Other content in complex else structures stays in place instead of moving merely to display a flattened list. Up to 16 branches can be added, also subject to the document's existing XML depth of 32 and structure budgets. Exceeding limits rejects the operation and retains original content. See [comparison conditions](xml-template-api.md#comparison-conditions-and-multiple-branches) for syntax and data types.

“Condition met” and “Other” each preview direct body content. Click body text to edit it in the same inspector; click a branch heading to open its full content list, or add a missing alternate branch. Each branch previews up to 40 items; enter the branch to view the rest. “Add content here” in branches and data loops appends paragraphs, images or tables. The top “Insert → Template logic” creates conditions or loops; cancellation preserves the original template and data.

The inspector displays the current node's body or data path. Direct child content of structural containers stays expanded, while paragraph inline structure starts collapsed. Captions, cross-reference prefixes and annotations use plain body-text editing. Corresponding properties are provided for loop paths/aliases, fragment references/prefixes, list markers, fixed-box sizing and body avoidance, contents/bookmarks and declared styles. Pure structural nodes do not show inapplicable position/size controls. Structures without dedicated controls remain editable through existing properties and “Node XML”; this does not mean every XML construct has a visual editor.

Table rows/columns and merges, grid row layout, inner-content duplication/deletion and full-width insertion all reside in the inspector. Selecting or switching containers does not change canvas-toolbar height. Narrow windows use a temporary inspector with descent and return in the same panel. Esc closes it and returns focus to its opening control.

After selecting a reusable fragment, click “Edit fragment content” to open its resource XML. Applying first compiles and lays out the complete candidate template. Failure retains the input and original resource; valid changes affect all references and support a single undo. Cancellation leaves the resource unchanged. If the resource changes during editing, reopen it to avoid overwriting updates. Fragment content currently uses an XML editor.

Property and body drafts preview live; switching nodes, saving or exporting commits valid changes. See [template-logic and inspector verification (Chinese)](../verification/designer-template-inspector.md) for the new entry points and fragment failure protection.

## Variables and Array Binding

“Body variables” in the inspector directly lists used references, path input, test values and field search. Place the caret at an insertion point or select text to replace, then choose a field or enter a path and click “Insert into body”. Click an existing variable to change its path, then “Update variable reference”. Only the selected reference changes; surrounding formatting, links and inline objects remain. Up to 200 references are listed; the rest remain editable in the body. “Insert variable” in the canvas in-place editor uses the same variable picker. Template variables read test data during preview and test export; bound results never overwrite them.

Text, numeric and boolean test values in existing root data can be edited directly in the inspector. Input updates the data draft and previews automatically. Multiline text uses a multiline field; numbers retain their original JSON numeric precision. Incomplete numeric input stays in the field with an explanation while the preview uses the last valid value. Navigation, export and undo commit data alongside body/condition drafts; continuous input can be undone together. Unedited strings retain original escape and newline tokens. Loop aliases resolve for each record, and the panel explains their data source. Use the test-data panel to change a specific record or add missing fields; loop records are not rewritten in bulk.

The picker displays only field paths, types and available scopes, without field values. Select existing fields or enter ASCII dotted paths such as `patient.name`; do not include `${}` or expressions in a manual path. Field enumeration includes enclosing `list`, `rows` and `each` aliases, with inner declarations taking precedence when names match. Data-table headers use the scope outside the container and cannot reference that table's current-row alias.

When inserting a “List item”, “Data list”, “Table” or “Data table”, first choose whether array-driven repetition is needed:

| Type | Source node | Relationship between content and data |
| --- | --- | --- |
| List item/numbering | `bullet`/`numbered` | One static list item whose body can contain variables; array length does not automatically add items |
| Data list | `list` | Generates a list item for each array member; the inner template defines each item's body |
| Table | `table` | The template explicitly declares rows and cells; cells can contain variables, but array length does not automatically expand rows |
| Data table | `rows` | Generates a template row for each array member; the header separately uses outer data |

After inserting a data list or data table through “Layout and containers”, the dialog requests the array path, iteration alias and repeated-content field. For example, array path `products`, iteration alias `item` and repeated-content field `item.name` produce `${item.name}` in each item's body. The default alias for data tables is `record`. After creation, continue editing template body text and adjust `items` and `as` in container properties. Expand “Choose array field” below the array path to search and select arrays directly from the outer scope.

An empty array still permits manual field paths such as `record.code`; it generates no repeated body content or data rows. If the record type cannot be inferred, the dialog asks for an actual field path or one real test record first. Object arrays use fields such as `record.code`; use `record` directly only when members are text, numbers or booleans. When no array is available, the dialog can offer a sample array. Confirming the suggested path writes the template and sample JSON together, with joint undo. New fields preserve existing JSON source and numeric tokens; large integers, long decimals and exponents are not reserialized through browser floating-point numbers. Canceling adds neither template nodes nor sample data.

Test data and templates save separately. “File → Save test data JSON as” downloads the companion data. After reopening template XML/ZIP, use “File → Load test data JSON” to load different data, then check preview or test export. The template retains variables, array paths, aliases and styles; JSON is not written into the template ZIP. See [variable and array-binding interaction verification (Chinese)](../verification/designer-bindings-ux.md) for operations and boundaries.

## Reading Check Results

The “Diagnostics” panel first shows the conclusion from the current preview or export check, then explains each reason, impact and recommendation. Fallback fonts are appearance notices: text remains, but glyphs, widths and line breaks can change. Character-level records are grouped by type; record counts are not error counts. Missing-glyph replacement receives a separate notice; add fonts and check the text. Expand affected locations and click an element to locate it on the design canvas while keeping the report expanded.

During test export, the report explains what will be simplified or removed. Selecting “Ignore warnings” does not remove those changes. Download automatically checks and continues or rejects according to policy; the report does not rewrite original templates or test data. Unknown notices explicitly require checking and are not automatically treated as safe. “Technical details” and “Download technical report” retain original information for further investigation.

## Editing, Saving and Reopening

1. The side toolbar provides document structure, project resources, test data and diagnostics; clicking a tool displays its content in the full sidebar beside the toolbar. The center editor offers canvas and XML; the right inspector edits element properties. The top “File” menu offers “New → Blank document/From sample”, Open, “Export template” and “Test export”. The top toolbar combines undo/redo, insertion, page settings and focus mode. Your own `.xml` and ordinary template `.zip` files can be opened.
2. Select a node in the structure tree or canvas. “Body content” for paragraphs, headings, list items and inline cells accepts text directly, with bold, color, size and decorations; images, links and fields remain independent objects. ID appears first in properties, and full structure remains editable through “Node XML”.
3. Choose text, layout containers or pagination/reference elements from Insert. Right-click blank space on the canvas paper or structure tree to insert at that location; actual body-flow positions follow layout. Data lists and data tables use an array-binding dialog; see [Variables and Array Binding](#variables-and-array-binding) for differences and field entry. Drag components and resources onto before/after insertion lines on the canvas. The structure tree reorders within the same container; move-up/down commands are also available. Expanded loops/conditions map back to the source template, so select their structural containers when reordering. Change array record order in bound JSON rather than treating an expanded item as an independent source node.
4. “XML” edits complete source, and “Test data” edits separate JSON. Property, XML and JSON input automatically calls the Java engine after a short debounce to compile, bind and paginate, without an Apply button. Canvas body text refreshes according to the selected editing mode. Invalid drafts show the reason in the status bar and diagnostics; the canvas retains the last valid preview and recovers automatically after correction. Source variables, conditions and loops are not replaced by bound body text.
5. “Export template” downloads a complete ZIP or XML only; “File → Save test data JSON as” downloads test data separately. After reopening the ZIP, use “File → Load test data JSON” to load companion data, then preview or test export. Data is not written into the template ZIP, so one template can continue binding different data.

“Export template” delivers the design. It defaults to a complete ZIP retaining original XML, fonts, images, reusable fragments and licenses, ready for continued designer editing or data binding through the library API. “Template XML only” downloads source alone, retaining variables, loops, conditions and styles; referenced fonts, images and fragments must be supplied separately. Download uses the current valid draft without writing bound preview content back into the template, and does not require test data to contain every binding value. Downloading XML alone does not mark unsaved resources as saved.

“Test export” uses current test data to generate PDF, DOCX, HTML, Markdown, SVG or PNG for checking binding results, layout and format compatibility. Generated files are this test's results; save and reuse the design through “Export template”.

Opening XML/ZIP or creating a document immediately clears the old canvas and hit regions before automatically previewing the new template. Pending previews from old sessions cannot overwrite the new document. If companion data has not been loaded after opening a template, missing values or layout errors appear in diagnostics instead of continuing to show the previous template's content.

Live preview does not change history or workspace versions. Switching structure nodes, saving, exporting and structural actions commit valid drafts as one workspace-undo entry. Committed text, insertion, reordering, properties and coordinates can be undone/redone in actual operation order. Ctrl+Z in an active text editor handles that text session; use workspace undo after completing it. Invalid drafts do not overwrite saved state, and new changes clear the redo branch. Normalizing Windows line endings for text-field display does not alone create a history entry. Plain-text panels do not flatten mixed content containing child elements into body text.

Local workspace source/data history retains up to 100 steps; server project/resource snapshots retain up to eight. After importing a resource and continuing text editing, undo can still reach the resource operation in actual order and redo can restore it. Cross-resource restoration validates the complete candidate first; failure neither advances history nor replaces the workspace. When older resources exceed server retention, the toolbar explicitly shows the undo boundary, and local history no longer promises their restoration. Active text sessions, workspace history and downloaded disk files are independent.

Saved bundles use [XmlTemplateBundle](xml-template-bundle-api.md), without a new file type. Structural changes may normalize XML quotes, attribute order and line endings while retaining content semantics, comments and template expressions. Unchanged source is not reserialized merely for preview. Structural application checks XML and compilation errors; missing data, reference resolution and layout failures are reported during preview/export, allowing further draft correction.

Each process has one workspace shared by browser tabs. Version checks reject stale-tab overwrite requests; reload after receiving a workspace-change notice. The file tab's modified state reflects only the current service session and does not guarantee that the browser has saved a file to disk. Closing the service clears its in-memory workspace and does not automatically restore drafts. Download the template and companion data before continuing later; downloaded files are unaffected.

## Creating a Document

“File → New” provides two entry points:

- **Blank document**: one A4 page, 42 pt margins and empty binding data, retaining only built-in fonts and licenses without sample text or images. Start writing through Insert or the canvas context menu.
- **From sample**: opens a sample picker showing each name and purpose. Selection creates an independent template and companion fictional data; cancellation preserves the existing workspace. Replacing unsaved content requires confirmation.

Eleven built-in samples cover an inspection report, dense static form, paginated long table, contents and cross-references, adverse drug reaction report form, service agreement, résumé, user manual, quotation, meeting minutes and weekly project report. The final six are multipage business documents covering clauses and acceptance matrices, photo-bearing two-column résumés, installation/operations manuals, grouped long quotations, discussion/decision ledgers and budget/risk reports. Complex tables, rich text and conditional styles remain editable. Every contract page header includes a sample company logo, version and number. Replace photos/logos in resources; complete template ZIPs retain images and source licenses. ## Continuous Canvas, Shortcuts and Context Menus

Actual engine pages form a continuous vertical sequence; scroll directly to view every page. Page selection and Previous/Next merely scroll to locations. Explicit page breaks appear as selectable helper markers, while automatic page/section boundaries appear as dashed lines. Helper markers do not enter exported files. Preview images load only for visible and neighboring pages; image URLs are released far from the viewport, while page geometry and hit regions remain.

Consecutive static list items can be selected as one list on the canvas. Dynamic-list items from the same source share one frame per page; frames do not span paper boundaries. Single-click a dynamic list to select its container and edit bindings; double-click an item to edit its template body. The structure tree supports individual selection, Ctrl-click addition/removal and Shift-click sibling ranges; canvas Ctrl/Shift-click also extends selections. Multiple siblings can be dragged or moved with directional commands as one ordered block. The bulk property panel shows only named properties shared by selected types and writes only fields actually changed. IDs and body text edit individually; bulk movement/deletion across containers is explicitly rejected.

Canvas and structure-tree context menus provide body editing, paragraph insertion before/after, duplication, move up/down and deletion. For multiple selection, movement/deletion affects the selected set. When an element has focus, Delete/Backspace deletes selected elements, Ctrl+D duplicates a single element, Alt+↑/↓ moves, and Enter/F2 focuses a single body editor. When clicking blank space displays document/section properties, Delete/Backspace and Ctrl+D do not modify content; selecting a canvas component again restores corresponding actions. Ctrl+Z undoes; Ctrl+Shift+Z or Ctrl+Y redoes. Text fields and body editors retain text deletion, selection and undo behavior, and open dialogs suppress element shortcuts. Deleted elements can be restored by undo; invalid drafts block commits.

## Pages, Headers, Footers and Margins

Click blank paper to select its `section`, or `document` when there are no sections. Click canvas space outside the paper to select the document. The inspector displays corresponding properties and “Pages, headers, footers and margins”, including for blank pages. Dragging blank space still draws a selection rectangle. You can also select `document`/`section` in the structure tree or choose scope through “Pages and regions” at the top. Paper choices are A4, LETTER, A3, A5, LEGAL and custom dimensions. A3/A5/LEGAL write explicit dimensions using existing XML rather than adding paper enums. Orientation is landscape/portrait; uniform and four-sided margins are configured separately. Lengths accept pt/mm/cm/in. Empty removes a local override and uses inheritance/defaults; explicit `0` differs from empty. Property descriptions appear in `ⓘ` tooltips beside fields.

When source changes repaginate a document, old preview pages associate with their section through section ID, retained unique child IDs or unambiguous original content, including after section renaming. If ownership cannot be established, refresh the preview and ask for reselection on the latest page. Current selection and changes remain; refresh failure does not switch targets. While viewing document properties, toolbar or Shift+F10 body insertion uses the current page's section. In-page “Insert content” buttons and blank-space context menus use the target page's section. Source, data, resource or preview changes invalidate open insertion menus. Already-selected insertion commands that are waiting or being configured also check before writing; reselect a position on the latest page. Generated contents pages do not belong to body sections; sectioned documents require selecting a body page before inserting body content.

To change paper, orientation, header or footer partway through a document, select the top-level body item that should begin the new section, then choose “New section” in its context menu or “Add element”. Ordinary body content becomes sections; an existing section splits at that item. The new section starts on a new page. Set `first-page-number` on the new section to reset displayed numbering; empty or `0` continues from the previous section. Root settings supply defaults; every section can independently override paper and page regions, including first/even-page variants. `{pages}` remains the entire document's final physical page count and does not reset with displayed numbering. Section boundaries lie between top-level body items; automatic page numbers cannot split a multipage paragraph/table internally. Selecting the first item of a section edits that section's settings directly.

Headers and footers each configure height, body gap and content, with default, first-page and even-page variants. Simple single-paragraph regions accept text directly. `{page}`/`{pages}` inserts a 24 pt-wide final page-number/total-page field; template variables such as `${page}` remain literal. Settings changes automatically lay out the preview; closing the panel writes undo history. Headers/footers on the canvas can be selected. Double-click a single-paragraph region to edit its body directly; select child nodes in the structure tree or edit highlighted XML for complex regions. Shared-source references navigate to their original declaration.

Each variant is a complete header/footer pair. A newly created variant leaves its disabled side empty instead of filling it from the default pair. Removing a local section declaration restores root inheritance. Clearing an inherited region requires an empty region with `height="0"`. Switching scope or variant retains the current valid draft; invalid XML must be corrected first. Excessive region height, margins exhausting body space and invalid dimensions fail explicitly without clipping, shrinking or changing units. See [paper settings](xml-page-settings-api.md), [page regions (Chinese)](../xml-page-regions-api.md) and [variants](page-variants-api.md).

Four-sided page margins, paragraph before/after spacing and table padding are configured separately. They are not conflated with CSS margin/padding, and mirrored binding margins are unavailable. “No margins” in page settings sets all four body margins to `0`. Headers/footers separately provide three inputs: distance from paper top/bottom, left and right. Explicit `0` can reach the edge; empty inherits the corresponding body margin. Page-region position participates in body-space reservation; leaving the paper or exhausting body space fails.

Page orientation is set through sections. Paragraphs, headings, list items, captions, images and tables can set `rotation` in clockwise degrees from `-180` to `180`; preview and PDF/SVG/PNG use the same graphics transform. Rotation scales proportionally inside the original layout box without changing line breaks, pagination or element position. Long narrow paragraphs/tables can shrink noticeably near right angles; increase line height or adjust table dimensions and inspect the preview. Multipage tables rotate each page fragment independently. DOCX/HTML/Markdown retain content but cannot retain angles and reject by default. WARN/IGNORE with DEGRADE lists each rotated element in the loss report.

## Tables, Rich Text and Complex Properties

For the selected node, the property panel provides named text/numeric inputs, color pickers and enum controls, with units, inheritance and restrictions. Paragraph controls cover font size, line height, alignment, role/color, first/subsequent indents, before/after spacing, line breaking, keep constraints, page breaks and orphan/widow control. Table controls cover four-sided padding, before/after outer spacing, borders and row splitting across pages. Selecting a column switches between fixed/proportional/bounded automatic widths; the interface clears mutually exclusive attributes from other modes. Selecting a cell configures column/row spans and text formatting. Merged cells must still pass complete-grid validation. Unknown attributes and attributes without dedicated controls remain in “Advanced XML attributes” and node source instead of disappearing silently.

“Compact grid”, “Spacious grid” and “Borderless” presets apply immediately, overriding the current table's padding, borders and direct-cell font size/line height; nested tables remain independent. Presets do not change merges, content, column widths or row-splitting settings. Style scope can be the whole table, header, body rows, a column or selected cells, with separate font size, line height, alignment, font role, text color and line breaking. Changes preview live and enter undo history when switching elements or saving. The current table model has no arbitrary cell backgrounds, per-edge line styles/colors or vertical-alignment controls.

“Cell layout / Merge” displays a grid including existing spans. Click a cell, Ctrl-select multiple cells or Shift-select a rectangle from the anchor; selected-cell styles remain adjustable after closing the panel. Merge requires a complete rectangle entirely within either header or body. Content stays in the top-left cell in row/column order, with line breaks separating ordinary inline content and rich text, links, images and fields retained. Split restores the physical grid, keeping original content at the top left and leaving other cells empty. Both are undoable. Merged paragraph alignment and line height follow the top-left cell. Dynamic `rows` body content permits only horizontal merges, without crossing data records. Cells with conditional rules require explicit rule removal before merge to avoid changing rule scope; splitting leaves rules in the top-left cell.

“Conditional styles” adds, edits or deletes rules for the current style scope. Data paths are lexical paths such as `record.score`. Conditions support boolean true/false, equality/inequality, numeric comparisons and text containment, without scripts. Matching rules override specified text properties in declaration order while retaining other values. Roles, color, font size, line height, alignment, underline and strikethrough can be set, with up to 64 rules per cell. Conditions reevaluate with bound data; resulting formatting enters PDF, DOCX and other output. Template ZIPs retain original rules; exported files contain only the current binding result. Body editing does not delete rules. Rules currently apply to inline cells, excluding block cells, backgrounds and borders. Missing values and type errors fail explicitly. See the [template guide](xml-template-api.md#conditional-cell-styles) for complete XML syntax and [Phase 111 (Chinese)](../verification/phase-111-designer-table-styles.md) for interaction and three actual output formats.

“Body content” directly edits a selected paragraph, heading, list item, link or inline cell. Select text to set bold, color, font size, underline or strikethrough. Formatting maps to existing XML inline declarations; images, fields and other structural objects remain indivisible markers. Paste is plain text and neither executes nor imports arbitrary browser HTML.

“Advanced inline fragments” continues to provide precise editing of fragment order, links, image resources/dimensions, baseline offsets and four page-number/numbering field types. In block cells, select an inner paragraph first. Body, property and node-XML drafts preview live; switching nodes commits valid changes. Fixed line height must accommodate the largest font/image, and fields need sufficient width. Images, fields, expressions and unchanged declarations retain original XML structure without plain-text flattening.

## Test Export and Losses

| Choice | Download | Semantics and restrictions |
| --- | --- | --- |
| PDF | One `.pdf` | Uses actual layout and retains currently supported navigation/references |
| DOCX | One `.docx` | Semantic mapping; pagination need not match PDF. Standalone captions, references, portable navigation and similar features degrade/discard according to actual reports |
| HTML | Self-contained `.html` | Semantic flowing output without paper geometry or portable navigation |
| MARKDOWN | `.md` | CommonMark/GFM content; styles, geometry, metadata, references and similar features report individual losses |
| SVG | Ordinary `.svg.zip` | One SVG per page; static pages discard interactive objects and report it |
| PNG | Ordinary `.png.zip` | One 96 DPI PNG per page; static pages discard interactive objects and report it |

DOCX tables retain independent column widths and merges; adjacent tables use their own column grids. Word editing/layout can change line breaks and pagination; inspect final display for dense tables.

The default action is `ERROR`, rejecting export on loss. `WARN` permits the selected degradation and emits warnings. `IGNORE` hides warnings while retaining actual losses. Invalid input, exceeded limits, cancellation and execution failure always fail.

Actions and treatments are independent. Format recommendations use `DEGRADE` for flowing layout and corresponding `DISCARD` for unmappable navigation/metadata/annotations. Actual features, reasons, treatments and impacts appear individually in preflight. Uniform `DEGRADE` or `DISCARD` can also be selected; if the target cannot perform that treatment, it rejects instead of substituting another treatment.

“Download file” automatically checks and actually encodes output, then downloads that same result on success without another confirmation. `ERROR` stops at the first rejected item and triggers no download. `WARN` continues downloading and displays warnings. `IGNORE` continues downloading and retains loss details without warnings. Every download uses the current template, test data and export configuration afresh; failure does not download an old result.

The export window directly displays a visual report with loss/warning counts, issue categories and each category's impact, treatment and recommendations. Click affected elements to locate them on the canvas. Table locations show source rows/columns; technical details can be collapsed. A rejection report lists only the first detected issue and does not mean all issues were checked. Reports also remain in diagnostics and can be downloaded separately as JSON. “File handed to browser for download” does not mean the browser has written it to disk.

## Budgets and Scope

- Designer input files are limited to 16 MiB. Template ZIP encoded and expanded totals are each 16 MiB, with 256 entries, 1,000,000 UTF-16 text units and 8,000,000 total image pixels. Existing engine resource and compilation budgets still apply.
- JSON must be an object containing objects, arrays, strings, booleans and bounded numbers, with at most 32 levels, 50,000 values and 1,000,000 UTF-16 units. `null`, duplicate keys and expression code are rejected.
- Each engine operation uses a 60-second cooperative timeout and 32 MiB output budget. “Cancel operation” is available. Preview is limited to 80 pages; use the library's [streaming entry points](streaming-replay-api.md) for bulk work. These are logical budgets, not process-memory or immediate-preemption guarantees.
- The service listens only on IPv4 loopback, validates Host, Origin and a per-startup session token, and neither connects externally, executes template code nor provides arbitrary file-path access. It serves one local workspace; a multi-user deployment needs separate identity, permission and runtime-isolation design.
- Free coordinates use bounded semantic boxes; other content continues using semantic flow. This application edits existing XML templates, without general graphical editing of arbitrary PDF/Word files or claims of compatibility with all browsers/mobile devices.
