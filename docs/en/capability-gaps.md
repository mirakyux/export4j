# Capability gaps and delivery tracking

Updated: 2026-11-13. Based on current source and independent verification records. The goal is a usable, controllable Java document-production engine; completion is not measured by counting feature names.

Status meanings: **Not implemented** means no complete implementation; **In progress** means implemented but verification incomplete; **Partially supported** means only an explicit subset; **Verified** means evidence covers the stated goal and boundaries; **Out of scope** records unavailable capabilities outside the current queue. Each item closes independently: a builder or similarly named method does not replace behavioral verification. Parent items summarize defined goals; extension subitems remain separate, and parents/children are not added together when counting completed items. Historical phases reflect their original scope; current status follows this catalog and the corresponding APIs.

See the [remaining plan (Chinese)](../remaining-capabilities-plan.md#后续扩展推进顺序) for delivery order. Broader file compatibility, editing, recovery, standards, and formats are tracked as independent gaps below; verification of existing subsets does not close these extensions. OCR is outside current scope; see GAP-23.

There are currently **3 independent unfinished items**: GAP-14.2, GAP-14.3, and GAP-22, under two parent items. GAP-12 is complete. Three-platform builds and temporary-key signed distribution passed remote CI for commit `cc132e7`; see [phase 105 (Chinese)](../verification/phase-105-publication-and-compatibility.md#远端-ci-验收).

The current candidate `0.1.0-rc.3` is published to Maven Central, with 16 libraries and the BOM consumable at that version. The `release` job in the [original publication run](https://github.com/mirakyux/export4j/actions/runs/43349185087) completed building, signing, uploading, and remote-consumer verification; for the separate GitHub Release recovery, see [release records/process](releasing.md#published-candidate-record). The current API gate uses the [published baseline (Chinese)](../api-compatibility.md) extracted from Central RC2 library JARs. GAP-14.3 still covers stable API, stable-release verification, and future-version compatibility. Historical statements below about unpublished artifacts refer only to their own batches.

The academic templates' [math subset](docx-math-api.md) is recorded separately: DOCX uses typed OMML, while PDF/SVG examples use restricted TeX vector layout; see [ManuWeave verification (Chinese)](../verification/manuweave-templates.md). This does not expand verified GAP-12 scope to arbitrary Word math extensions or imply a cross-format equation node, TeX↔OMML converter, or complete LaTeX runtime in the general document model.

[Editable body columns](column-flow-api.md) separately provide ColumnFlow/XML/designer entry points for 1–3 continuous columns, intervening full-width tables/images, and resumed columns. [Semantic grids](grid-layout-api.md) add 1–12 tracks, regions spanning some tracks, item-boundary editing, and atomic grid-row pagination. They can be combined as siblings. Native DOCX/Web mapping, row-spanning items, auto placement, and mutual nesting remain unavailable. Explicit conversion retains only sequential content with reported layout loss; see [column verification (Chinese)](../verification/semantic-body-columns.md) and [grid verification (Chinese)](../verification/editable-grid-layout.md). Existing component-column/CSS-Grid scope is not expanded.

[Phase 106 (Chinese)](../verification/phase-106-security-and-compatibility-corpus.md) adds a fixed conversion/rejection corpus, complete DOCX ZIP validation, dependency-advisory gates, and the `0.1.0-rc.1` candidate API baseline. This batch passed 1,787 Java tests, 16 paths/32 outputs/73 control checks, and local signed-artifact verification. Its new CI steps had no remote-run evidence, and no formal release was performed in that batch.

[Phase 107 (Chinese)](../verification/phase-107-windows-reader-compatibility.md) completes this round's executable Windows Word/PDF-reader opening, searching, editing, saving, reopening, and final-JAR reimport, fixing DOCX compatibility-mode declarations and PDF reader-application metadata acceptance. Its latest build passed 1,792 tests, fixed-corpus checks, and checks for printing dependencies. Cross-platform tests, foreground browser interaction, and that batch's new CI were not performed; changed bytes from that round were not signed again.

[Phase 99 (Chinese)](../verification/phase-99-layout-fonts-streaming-graphics-closure.md) fully verifies the original remaining lists and existing extension subitems for GAP-03/08/09/21. All four parents close without new gap numbers. Each API retains explicit input subsets, resource budgets, and tool-compatibility boundaries. Subsequent DOCX, document-CSS, and designer verification uses their existing items; cross-platform/reader compatibility and formal distribution were not closed by that phase. Phase 98 and earlier historical records do not describe current unfinished status.

[Phase 108 (Chinese)](../verification/phase-108-designer-and-business-scenarios.md) completes GAP-13's independent HTML designer and four complete business examples. Its build passed 1,804 Java tests, API compatibility, an isolated Maven consumer, and checks for printing dependencies. [Phase 109 (Chinese)](../verification/phase-109-designer-editing-controls.md) adds pages/regions, tables, rich text, typed properties, and formatting/highlighting controls. [Phase 110 (Chinese)](../verification/phase-110-designer-canvas-and-interactions.md) verifies a continuously paginated canvas, direct body editing, persistent resources, shortcuts/context menus, and list sorting. Designer browser/output evidence is recorded separately and does not expand GAP-14.2's platform matrix.

Since `0.1.0-rc.2`, [ordinary-document page-by-page export](paged-document-api.md) releases completed pages' IR/Display Lists from a complete input model and reuses bounded painting resources; the disk-indexed PDF backend copies completed live page objects directly. [This verification (Chinese)](../verification/paged-document-export.md) separately records final pagination semantics, replay consistency, failure atomicity, and finite capacity. It does not change single-pass row-source contracts or establish constant memory for arbitrary complete models, largest blocks, or footnote plans. Earlier `0.1.0-rc.1` does not contain this entry point.

Ordinary content blocks can also be supplied on demand through `BlockSource`: `exportSemantic(PageSettings, Factory)` writes in one pass after an accurate total-page declaration; `exportReplay` explicitly reopens a stable snapshot for two passes, reducing complete-input retention. This path supports page fields/fixed regions. Contents, future references, cross-section behavior, and footnote reflow still use complete-model entry points. The largest block, keep chain, unique IDs, and page summaries retain finite budgets; see [ADR-0112 (Chinese)](../adr/0112-incremental-block-source.md).

## Independent extension gaps

These items track extension goals and actual verification without recounting verified page selection, merging, basic forms, text replacement, or four-format conversion. Priorities apply to the next delivery unit. Historical parent-subset verification does not establish implementation of these extensions. Define accepted inputs/combinations first, then add source, behavior, and independent-file evidence; relaxed preflight or ignored losses cannot create compatibility.

### Unsupported-content editing policies and loss reports

The following contract is implemented/verified in existing adapter subsets of [unified conversion](document-conversion-api.md). Older entry points retain defaults; new formats/original-package editing require individual verification. Policy enum values do not imply feature support.

| Dimension | Target behavior and verification conditions |
| --- | --- |
| Actions and precedence | Default ERROR, with explicit global/per-format/feature/operation precedence. WARN returns a warning and applies explicit handling; IGNORE applies identical handling without that warning. Both retain queryable actual-loss reports; IGNORE results cannot be labeled lossless |
| Handling | Separately declare rejection, skipping an operation, degradation to a supported representation, or explicit property/content dropping. Skipping specifies whether it affects one match, a block, or the request. Preserve-original is available only when complete source structure remains and the target has a verified preservation path; otherwise fail explicitly |
| Preflight and execution | Before writing, inspect the edit plan/target format and list possible losses/impossible actions, bound to the same snapshot/configuration. After execution, distinguish predicted loss, actual loss, and skipped actions. Failed/unexecuted work is not success; preflight does not guarantee I/O success |
| Report locations | Include stage (import/edit/export), source/target formats, feature, operation, section/region/block ID, physical-cell path, and applicable UTF-16 range. Retain locatable reasons/actions/handling/impact without echoing body text/full paths/credentials by default |
| Loss inventory | Identify deleted text/images, degraded fonts/styles, changed widths/positions/pagination, fields flattened to values, broken links/bookmarks/numbering/cross-references, and dropped comments/revisions/forms/metadata. Check unedited content too |
| Nonignorable failures | WARN/IGNORE cannot admit invalid Unicode, malformed structures, invalid references, insufficient permissions, budgets, cancellation/timeouts, or I/O failures. Macros/scripts/implicit external access remain rejected. Signature-related changes require their independently verified contract; ignoring warnings cannot silently remove signatures or claim continued validity |
| Cross-format boundaries | Report specific degradation when a target cannot express content, without arbitrary lossless-round-trip claims. Unknown source structures that cannot be retained cannot masquerade as unchanged saving. PDF-page semantic recovery remains GAP-20; policy cannot supply nonexistent content |

Shared verification must cover ERROR failure before output, identical WARN/IGNORE handling/queryable losses, individual precedence, skip scope, failed preservation, unedited-content loss, unchanged input snapshots, and old-target protection on failure.
