# Development

These conventions apply to Java implementation, tests, examples, and build configuration. There are currently 19 Gradle subprojects: 16 libraries, a BOM, examples, and the optional designer.

## Technology and builds

- Java 21 LTS is the initial baseline. Verify compatibility before adopting dependencies.
- Use Gradle multi-project builds, Kotlin DSL, and a complete committed Wrapper.
- Unify Java versions through toolchains and use UTF-8 sources.
- The root package is `com.mirakyux.export4j`, under `src/main/java/com/mirakyux/export4j`; tests use the same package structure, and the Gradle group matches the root package.
- Pin Gradle and plugin versions; manage third-party versions in the version catalog.
- `export4j-bom` aligns public modules. The Maven Central group is `com.mirakyux.export4j`; see [releases](releasing.md) for publication state and permissions.
- Keep core dependencies necessary. Explain the purpose, alternatives, and maintenance cost of new frameworks or tools.

## Repository content

Documentation, examples, and verification commands use repository-relative paths. External tools use commands on PATH or explicit configuration. Do not commit personal directories, machine identifiers, real credentials, session authorization, or agent assignments. Resources and examples must be publishable.

Build outputs, logs, private configuration, and signing material belong in ignored directories. Ignore rules affect only untracked files; committed secrets remain in history, and deleting working files does not erase that history.

## Build commands

On Windows run `.\gradlew.bat build`; on Linux/macOS run `bash ./gradlew build`. Root `build` aggregates all modules, while root `test` runs tests only. `:examples:run` demonstrates precise drawing; `:examples:textPdf` Chinese/English line layout; `:examples:flowPdf` semantic paragraph pagination; `:examples:tablePdf` cross-page tables; `:examples:componentPdf` basic interactions; `:examples:advancedPdf` an integrated report; and `:examples:benchmark` a large-document layout baseline.

See [examples](examples.md) for common tasks and output directories. To verify local artifacts and a consumer:

```powershell
.\gradlew.bat build sbom publishLocalBundle
powershell -NoProfile -File scripts/verify_local_consumer.ps1
```

Independent format/rendering checks use Python 3.11+, [pinned verification dependencies](../../scripts/requirements-verification.txt) in an isolated environment, and Poppler. PDF/A, signing, and application compatibility additionally require tools such as veraPDF, OpenSSL, or Word as applicable. These are not library runtime dependencies. Select checks using the [verification matrix (Chinese)](../../.agents/skills/develop-export4j/references/verification.md).

[GitHub Actions](../../.github/workflows/build.yml) runs on `main` pushes, pull requests, and manual dispatch, covering Java 21 on three platforms, API checks, coordinate consumers, driverless execution, and signing with temporary keys. Remote results, architectures, and coverage boundaries are recorded in [phase 105 (Chinese)](../verification/phase-105-publication-and-compatibility.md#远端-ci-验收).

The fixed corpus is generated by `python scripts/create_compatibility_corpus.py`, which creates independent positive/negative OOXML controls. Run the consumer's `compatibilityCorpus`, then independently inspect content, losses, and dual rendering with `scripts/verify_compatibility_corpus.py`. The generator requires a new directory to avoid stale outputs. Runtime advisory gates use `scripts/test_dependency_audit.py` and `scripts/audit_dependencies.py`; the latter requires OSV network access. Commands, dependency upgrades, and historical verification boundaries are in [phase 106 (Chinese)](../verification/phase-106-security-and-compatibility-corpus.md); later RC2 workflow results are in [published candidates](releasing.md#published-candidate-record).

Java compilation uses `-Xlint:all -Werror`. `gradle/libs.versions.toml` is the version catalog, and module lockfiles fix resolved versions. Intentional upgrades use `--write-locks` and update dependency/license records.

## Source organization

Production code lives in `src/main/java`; tests in `src/test/java`. Resources use the corresponding `resources` directories, and test output goes under build directories.

Fixed fonts live in `assets/fonts`, referenced by examples and relevant test resource sets. Core libraries do not bundle example fonts. Check byte hashes, sources, embedding rights, and adjacent licenses when updating resources.

Organize packages by domain responsibility. Avoid unbounded `util`, `common`, or oversized manager classes. Module, file, and type names express responsibility; public artifacts use `export4j-*`.

Separate public extension interfaces from implementation. Use the narrowest access by default; do not expand production API visibility merely to test it.

## Code style

- Four spaces, no tabs; UTF-8 and LF.
- `UpperCamelCase` types, `lowerCamelCase` methods/variables, `UPPER_SNAKE_CASE` constants.
- Explicit imports, without wildcards.
- Prefer simple, clear code; use `var` only where the local type is immediately apparent.
- No preview features by default, and no Lombok hiding model behavior.
- Remove unused imports/variables and unreachable code. Fix generic, nullability, and resource warnings in contracts and implementation.
- Scope necessary `@SuppressWarnings` narrowly and explain why.
- Comments explain units, algorithm foundations, and tradeoffs rather than repeating code.

New project Java files use this license identifier. Copyright notices, when present, must name the actual rights holder:

~~~java
// SPDX-License-Identifier: Apache-2.0
~~~

## Data models and public APIs

Public authoring/configuration APIs prefer `builder()`, named setters, and `build()`. Required business identifiers may be builder-factory arguments. Nested structures use synchronous `Consumer<Builder>` callbacks, snapshotting when the callback returns without retaining mutable child builders. Reusable styles offer `toBuilder()`. Preserve existing short constructors and static factories. Do not mechanically add builders to results, commands, exceptions, or SPIs. See the [fluent API](fluent-api.md) and [ADR-0018 (Chinese)](../adr/0018-fluent-authoring.md).

Prefer immutable values. A `record` is not automatically deeply immutable: collections, arrays, and mutable objects still require defensive copies or explicit ownership.

Validate required parameters at boundaries. Return empty collections for no elements and `Optional` for optional singular results, without using `Optional` fields or parameters. Document special null semantics.

Public API/SPI Javadoc covers:

- Parameters, results, units, coordinate direction, and baselines.
- Defaults, ranges, and validation.
- Resource ownership, closing, and thread safety.
- Expected exceptions, unsupported capabilities, and downgrade behavior.

Use interfaces for open extension points. Reserve `sealed` for genuinely closed internal hierarchies so third-party backends/components remain extensible.

Public signatures, exceptions, and returned objects must not expose implementation types such as PDFBox, including through generic arguments or parent types.

## Numbers and text

Lengths and coordinates follow [architecture conventions](architecture.md). Avoid unexplained magic numbers. Centralize conversion at input/output boundaries rather than spreading millimeter/pixel/point conversion through layout.

Geometry tests use justified tolerances and distinguish absolute from relative error. Do not use a single large tolerance to hide algorithm errors. Pixel resolution differs from logical length.

Never infer text width or glyph count from Java `char` counts. Cover Chinese, mixed text, surrogate pairs, combining characters, and missing glyphs. Complex-script support is bounded by actual implementation and verification.

Layout and painting consume consistent fonts, glyphs, and metrics. Backends must not remeasure with default fonts or change layout.

See [fonts and text](text-api.md). Line height is fixed baseline spacing, with common ascender/descender values across the stack. Line breaking uses JDK ROOT-locale rules; tests record the JDK version. Emergency breaks in very narrow regions do not promise complete Chinese prohibition rules.

The [layout API (Chinese)](../layout-api.md) distinguishes semantic paragraphs, paragraph-local lines, and page fragments. Preserve original source across pages. Numerical boundaries allow only floating-point-rounding tolerances; shrinking or clipping must not substitute for failure when content cannot fit.

Traverse mixed content through `Document.blocks()` and `LayoutPage.elements()`. Cell sources use block, row, column, and UTF-16 ranges. Repeated headers preserve source and are marked separately. Paragraph-only compatibility views must not paint complete documents. See [tables](table-api.md) for constraints and budgets.

Components follow core SPI: local top-left coordinates, independently balanced immutable command snapshots, and diagnostics. Ordinary body components measure once against full-page content bounds. `PageableComponent` returns ordered nonempty fragments, with the first allowed to use remaining height; final page numbers must not influence size. Page-region components measure after the final count is known. Positioned regions stay within their parents. Custom commands outside their viewport are not automatically clipped; implementations must clip explicitly.

Reserve headers/footers through `PageTemplate.bodySettings` before body pagination. Sections reserve the maximum regions and distinguish displayed numbers from physical indices. Footnote reservation/continuation must be bounded and reserve the first line for new footnotes. Multiline references reserve dimensions before final pagination. Contents/bookmarks resolve against final offsets. Forms check field trees, widgets, valid values, and appearances, plus independent filling, saving, and reopening. See [components (Chinese)](../components-api.md) and [production capabilities (Chinese)](../production-api.md).

## Exceptions and diagnostics

Invalid entry arguments identify the parameter. Reading, layout, and export failures retain original causes and add stage/resource context.

No swallowed exceptions, empty `catch`, unlimited retries, or success after failure. Partial output is not success; contracts describe stream/file state after failure.

Diagnostics use stable codes and structured locations; human messages may evolve. Clearly distinguish caller-accepted downgrades from unrecoverable errors.

Libraries do not print to stdout, set caller-global logging, or record full content/credentials by default. `FontGroup` strict/placeholder policy applies throughout body, contents, regions, and nested components. Replacement emits structured WARNINGs while preserving original code points and UTF-16 positions; callers decide how to display them. Missing glyphs in form values still fail.

## Resources, concurrency, and security

Own files, backend documents, and decoded resources use `try-with-resources`. Borrowed streams remain open by default; ownership transfer is explicit.

Mutable builders and document contexts are task-local by default. Immutable results may be shared when allowed by contract. Shared caches need capacity, synchronization, eviction, and release policies.

Treat files, fonts, images, and compressed content as untrusted. Limits specify units, defaults, and over-budget diagnostics, and are verified on large or adversarial inputs.

Do not automatically download fonts/remote images or execute macros/scripts. Importers prevent archive bombs, path traversal, and unintended external entities.

Generation, import, editing, and conversion must not depend on printer drivers/services or Office/browser processes. Ordinary paths support headless JVMs with explicit caller fonts/resources. External applications serve only independent compatibility verification. After runtime dependency changes, run `scripts/verify_driverless.py` to inspect production JARs/runtime hashes and generation/conversion with printing classes rejected. See [architecture](architecture.md).

## Test strategy

| Change | Verification |
| --- | --- |
| Documentation only | Links, headings, terms, factual state |
| Model/validation | Valid/invalid input, immutability, public contracts |
| Geometry/drawing | Coordinates, transforms, clipping, state restoration, output structure |
| Fonts/text | Measurement/output consistency, Unicode mappings, missing glyphs, fallback |
| Layout/pagination | Line boxes, bounds, order, no loss/duplication, progress, oversized content |
| Format adapters | Round trips within declared scope, downgrade diagnostics, failures |
| Resources/concurrency | Normal/failure cleanup, limits, task isolation |

Use JUnit for observable behavior, algorithm boundaries, and real regressions, rather than merely checking accessors or duplicating implementation.

PDF verification combines structure, extracted text, fonts, and images. Phase acceptance also uses independent parsing/rendering; reading output only with its generating backend is insufficient.

Visual regression fixes renderer versions, fonts, resolution, and resources. `python scripts/verify_advanced_pdf.py` checks structure, interactive fill/save, Poppler/PDFium rendering, and repository PNG baselines. Dependencies are pinned in `scripts/requirements-verification.txt`. Explain thresholds and causes, and explicitly use `--update-baseline` only after inspecting every page; never refresh baselines merely to pass. See [advanced acceptance (Chinese)](../verification/phase-3-advanced.md).

Performance records specify samples, fonts, JDK, hardware, warmup, concurrency, and method. Establish baselines before targets; do not invent unmeasured throughput/memory goals.

Production verification uses `build sbom publishLocalBundle :examples:production`, `scripts/verify_local_consumer.ps1`, and `python scripts/verify_production.py`. Independently inspect all new PDF pages, DOCX semantics, static rendering, actual SBOM hashes, and BOM dependencies. JDK java.desktop may run headless, but complex text uses only explicit fonts. Local Maven output is `build/repository`.

## Completion criteria

Before delivery:

1. Behavior meets acceptance requirements and module dependencies remain acyclic.
2. Public APIs, ownership, and failure behavior have explicit contracts.
3. Relevant checks ran and new warnings are addressed.
4. New dependencies/resources and licenses are registered.
5. Documentation, examples, and ADRs match the final implementation.
6. Delivery states actual commands, results, and unverified scope.

Record missing tools or failed commands. Static checks, unit tests, independent verification, and publication are distinct outcomes and cannot substitute for each other.
