# Capabilities and API navigation

This page summarizes the available document generation, import, editing, and conversion entry points. Start with the [documentation index](README.md) and [runnable examples](examples.md); individual API guides define their precise input subsets and calling contracts. Historical verification records cited below establish only their own batch. See the [capability gap catalog](capability-gaps.md) for current completion status.

[Body columns](column-flow-api.md) provide a saveable ColumnFlow/XML columns model and designer component, supporting 1–3 columns, ratios/gaps/balancing, and full-width tables/images inserted between column sections before resuming within the remaining page height. Actual paragraph/table provenance is retained. DOCX/Web support sequential flattening only with explicit DEGRADE and reported layout loss; native column mapping is not yet available.

[Editable grids](grid-layout-api.md) provide GridLayout/GridItem, XML grid/item, and designer entry points: 1–12 equal-width tracks, row/start-track/track-span values, point gaps, and actual item boundaries. Each grid row paginates atomically and can share a page with continuous columns. DOCX/Web preserve sequential content and report layout loss with explicit GRID_LAYOUT/DEGRADE. Nested grid/column combinations, items spanning rows, and arbitrary CSS Grid are unsupported.

[XML template source editing and resource ZIPs](xml-template-bundle-api.md) reuse the existing template adapter, retaining editable main source, fragments, images, explicit fonts, and license text. Ordinary ZIPs can be saved/reopened and continue through `XmlTemplate → DocumentTemplate`. This is not model recovery from arbitrary rendered documents.

[Saving semantic models as XML (Chinese)](../xml-model-saving-api.md) supports body/sections, rich text/separate list markers, tables/recursive block cells, four field kinds, and images, retaining existing formatting and original literal values and integrating with unified conversion. [Page-region saving (Chinese)](../verification/phase-79-xml-region-saving.md) preserves default/first/even headers and footers, shared sources, and ordered layer positions. [Phase 80 (Chinese)](../verification/phase-80-xml-semantic-saving.md) additionally preserves explicit annotations/markers, Caption, and heading/list text links. `renderComplete(data)` returns both document and annotations; three-round controls, editing, a 10-page PDF with two renderers, and Web loss reconciliation passed. [Phase 81 (Chinese)](../verification/phase-81-xml-cross-reference-saving.md) completes XML saving/binding of standalone CrossReference, including cross-section PAGE/NUMBER, multiline references, fragment/loop targets, and actual edits. Unmapped blocks fail by default; only explicit policies allow continued processing with reported loss. Callers provide fonts/licenses explicitly. XML preservation does not expand DOCX/Web adapter capabilities.

XML static page configuration was verified in [phase 36 (Chinese)](../verification/phase-36-xml-page-settings.md). The optional first `page` child of the main root supports paper size, paired width/height, orientation, and four margins; lengths accept pt/mm/cm/in. Undeclared values retain Java defaults; see the [page guide](xml-page-settings-api.md). [Phase 41 (Chinese)](../verification/phase-41-xml-page-regions.md) adds [fixed headers/footers (Chinese)](../xml-page-regions-api.md), independent themes, and final page numbers. [Phase 42 (Chinese)](../verification/phase-42-sections-and-docx-regions.md) adds page-region images/tables, XML sections, and default DOCX page regions. Global font roles/colors were connected in [phase 60 (Chinese)](../verification/phase-60-theme-appearance.md); first/odd/even regions were verified in [phase 61 (Chinese)](../verification/phase-61-page-variants.md); [XML backgrounds/foregrounds (Chinese)](../page-overlays-api.md) were verified in [phase 62 (Chinese)](../verification/phase-62-page-overlays.md). For static HTML/CSS cascading and explicit document-layout mode, see the [import guide](html-import-api.md); this does not imply a complete browser.

[Fixed page-region font roles (Chinese)](../page-region-fonts-api.md) retain engine-registered roles, missing-glyph policies, and final page context. Standard components can now select font groups and author fixed rich text directly with [FontRoleScope/RichTextComponent](component-text-api.md), without custom delegates. Deferred SemanticTable still cannot enter fixed page regions. XML regions use the same reservation/final-composition path through PageDocument and PageRegionTemplates; their themes do not cascade into the body.

[List markers (Chinese)](../list-markers-api.md) independently retain a complete InlineStyle; standard DOCX uses the selected level's run properties. [XML text defaults (Chinese)](../xml-text-defaults-api.md) configure roles/colors separately for body/headings/cells, preserving explicit local overrides, named complete styles, and nested-cell scope. See [phase 38 (Chinese)](../verification/phase-38-component-text.md), [39 (Chinese)](../verification/phase-39-list-markers.md), and [40 (Chinese)](../verification/phase-40-xml-text-defaults.md). The overall trial boundary is in the [readiness assessment (Chinese)](../readiness-assessment.md).

The project uses `com.mirakyux.export4j` and its existing Maven coordinates, with 19 modules: 16 libraries, the BOM, examples, and the optional designer application. Optional `export4j-opentype` provides native text capabilities without forcing JNI into the core. The original capability-expansion example is [CapabilitiesExample](../../examples/src/main/java/com/mirakyux/export4j/examples/CapabilitiesExample.java); current scope is determined by each API and its verification.

[Native Word equations](docx-math-api.md) provide an adapter-owned typed tree and standard OMML reading/rebuilding for fractions, radicals, scripts, integrals, matrices, delimiters, functions, and limits. `readMath`/`writeMath` preserve editable equations; ordinary reading explicitly rejects math content. Restricted TeX vector layout for PDF/SVG currently lives in the [ManuWeave example](examples.md#mathematical-formulas). The general model has no cross-format equation node or automatic TeX↔OMML conversion. See the [dedicated verification (Chinese)](../verification/manuweave-templates.md) for implementation and actual Word application actions.

## Existing PDF processing and semantic recovery

[Standard-file recovery](model-recovery-api.md) offers ordinary files, XML/resource-ZIP sidecars bound to exact bytes, or explicit single-file embedding. See [phase 82 (Chinese)](../verification/phase-82-model-recovery.md) for three rounds over seven outputs, 49 A→B→A combinations, and actual editing. [Phases 83 (Chinese)](../verification/phase-83-embedded-html-recovery.md) and [84 (Chinese)](../verification/phase-84-embedded-comment-recovery.md) provide HTML/Markdown/SVG comment envelopes; [85 (Chinese)](../verification/phase-85-embedded-png-recovery.md) adds single-page PNG ancillary chunks; [86 (Chinese)](../verification/phase-86-standard-container-recovery.md) adds PDF attachments and DOCX/PNG-page-ZIP members, recording standard readers, external rewrites, and measured sizes. Modified files reject stale models or use explicit restricted import; lossy exports do not conceal source copies. Semantic recognition of arbitrary files without recovery information and lossless third-party resaving remain unavailable.

[Phase 87 (Chinese)](../verification/phase-87-complex-lossy-recovery.md) extends table/image/list round trips to seven outputs and 49 complex A→B→A combinations. With explicit DEGRADE, `reimportOnLoss` rebuilds the recovery model from this export's exact output bytes and retains actual import losses; it does not include a richer source candidate. HTML column groups and single-segment headers allow explicit degradation. Separating explicit list markers from body text prevents accumulated prefixes across rounds. Native numbered references were verified separately for PDF/DOCX preservation and static Web degradation; static backends reject interactive links. Broader semantic combinations and application Save As compatibility are not established by this work.

[Phase 88 (Chinese)](../verification/phase-88-section-recovery.md) adds three rounds over six formats and 36 A→B→A combinations for two sections/four pages, shared regions/variants/overlapping layers, nested tables, and vertical spans. Exported scrolling containers inside HTML cells can explicitly degrade/be dropped under `TABLE_CELL_CONTAINER`. DOCX layer dropping and Web section/selection-rule losses are recorded against actual files. Single PNG still rejects multipage input. Broader annotation/reference combinations and real application resaving remain separate verification work.

[Phase 89 (Chinese)](../verification/phase-89-navigation-recovery.md) adds three rounds over four formats and 16 combinations for annotations/captions/references. [Phase 90 (Chinese)](../verification/phase-90-recovery-closure.md) completes overall GAP-24 verification: [DocumentNavigation (Chinese)](../portable-navigation-api.md) retains automatic heading selection, manual bookmarks, and contents text/layout/colors, resolving current headings and final page numbers after recovery. Combined sections, region variants, layers, nested merged tables, images, annotations, and references complete three rounds and 16 A→B→A combinations. PDF preserves the complete model for this combination; DOCX/Web reimport actual files under explicit loss policies, and dropped declarations do not return. After actual Word editing/Save/close/reopen, missing/stale information fails by default; explicit region geometry and loss policies are required to read current content. Arbitrary application compatibility and external structure recognition remain independent gaps.

[PdfAdapter](pdf-adapter-api.md) provides separate entry points for static copying, page editing, passive-object editing/composition, rendering/extraction, optimization, text replacement, regional redaction, and semantic recovery. Public signatures expose no third-party types. Every entry point retains its permission, signature, safe-parsing, budget, cancellation, and atomic-path-output boundaries; support for an object in another entry point does not automatically relax them.

Arbitrary lossless PDF editing/layout recovery is unsupported, and OCR is outside scope. Callers must specify all redaction regions; sensitive information is not detected automatically. Coordinate systems and font/page subsets are defined by their respective APIs.

External PDFs' [embedded static CFF fonts (Chinese)](../pdf-font-compatibility-api.md) work through rendering, text replacement, raster redaction, and semantic recovery. New PDFs support native embedding of static CFF body fonts. Nonembedded fonts receive no implicit system substitution; entry-point boundaries for complex streams and interactive structures remain independent.

[Explicit source-font mapping (Chinese)](../pdf-font-compatibility-api.md#渲染与脱敏的显式源字体映射) lets rendering/raster redaction use caller-supplied static TrueType to replace simple fonts without programs, preserving source encoding/widths and reporting appearance replacement loss. It does not expand text-editing/semantic-recovery font scope. Semantic recovery separately accepts explicitly allowlisted ordinary opaque ExtGState; transparency, soft masks, unknown keys, Forms, and clipping retain their respective boundaries. See [phase 91 (Chinese)](../verification/phase-91-pdf-source-fonts-and-graphics-state.md) for both implementations and independent controls.

[Phase 92 (Chinese)](../verification/phase-92-pdf-form-recovery.md) adds recovery of actual ordinary opaque Form invocations: nested/repeated instances, local/inherited resources, positive proportional scaling/translation, transformed text colors/sizes, images, and physical provenance. Implicit BBox checks actual glyph outlines and image rectangles; fully hidden content is dropped with reported loss. Original Form editing, explicit clipping, and transparency composition excluded from this phase are expanded in later phases.

[Phase 93 (Chinese)](../verification/phase-93-pdf-compatibility-closure.md) completes the original GAP-10.6 remainder: dictionary encodings/horizontal CID source-font mappings, legacy Type1/static Type3 painting, isolated shared-Form invocation editing, more graphics states, explicit clipping/transparency composition, and reading/preserving passive layers/tags in the original document. Layers/tags require explicit `allowPassiveStructures(true)`; reading uses default VIEW and does not expose text from disabled layers. Cross-document copying/composition remains strictly rejected. See the [compatibility matrix (Chinese)](../pdf-passive-structures-api.md) for preservation, editing, and recovery scope per entry point.

Pages that can render but cannot be expressed by the current semantic model may explicitly use `PDF_STRUCTURE / DEGRADE` to recover the whole page as a flowing image for PDF/DOCX/HTML/Markdown. Body text, vectors, and structure cease to be editable, with itemized losses. `SKIP_BLOCK` can still skip whole pages. ERROR is the default; WARN/IGNORE use consistent handling. Invalid input, missing glyphs, budgets, and cancellation still fail. Source-font mapping serves only rendering/raster redaction and does not implicitly enter semantic recovery.

## HTML and Markdown output

The [Web adapter](web-export-api.md) directly maps semantic documents to HTML5 and CommonMark/GFM content, with global/per-feature ERROR/WARN/IGNORE. HTML retains merged/nested tables, styles, and embedded images; Markdown explicitly degrades formatting loss while preserving anchor content. Strict behavior is the default; invalid input, limits, and cancellation cannot be ignored. See [phase 43 (Chinese)](../verification/phase-43-web-exports.md). HTML/CSS input uses the separate entry point below; semantic conversion does not promise PDF layout round trips.

## Offline HTML/CSS input

[HtmlImporter](html-import-api.md) supports an explicit element/attribute/static-CSS subset, including priority/inheritance, explicit images, lists, two-dimensional spans, and bounded recursive block cells. Source positions and actual losses are available. Hidden content, margin collapsing, and unmodeled structures are not silently treated as lossless. Scripts/implicit external access are rejected; see [phase 46 (Chinese)](../verification/phase-46-html-import.md). Complete browser layout is not promised.

## General Markdown input

[MarkdownImporter](markdown-import-api.md) supports a CommonMark/GFM subset with emphasis, links, nested lists, tables, strikethrough, hard breaks, and explicit images. Code/quotes and similar content report losses through shared policies; preflight binds the candidate, and IGNORE retains actual losses. There is no variable binding or implicit external access. See [phase 45 (Chinese)](../verification/phase-45-markdown-import.md); this is neither complete GFM nor arbitrary lossless Markdown round trips.

## Semantic editing

[DocumentEditor (Chinese)](../semantic-editing-api.md) supports block/physical-cell editing, text/images/style changes, literal search/replacement across runs, and input-snapshot preservation for Document/PageDocument/SectionedDocument. Shared policies distinguish ERROR/WARN/IGNORE from skip/degrade/preserve; preflight binds the exact candidate, and IGNORE still returns actual losses. Integrity, Unicode, budgets, and cancellation cannot be ignored. See [phase 44 (Chinese)](../verification/phase-44-semantic-editing.md); this does not establish lossless editing of general source DOCX or existing PDFs.

## Shared text and fonts

DOCX [style cascading (Chinese)](../docx-style-import-api.md) supports defaults, basedOn, character styles, and direct formatting, with explicit font-family mappings selecting actual roles and reported graph-expansion losses. [Original-package editing (Chinese)](../docx-editing-api.md) changes ordinary text while preserving unedited structures. The [typed semantic model](docx-semantic-api.md) separately represents floating images/actual text boxes, image transforms, comment ranges, insertion/deletion/move/format revisions, content controls/legacy forms, and updateable contents declarations. Editing relocates anchors before generating standard OOXML. Projection into the general model reports losses individually; older ordinary semantic entry points also check unedited proprietary structures. Arbitrary lossless Word round trips and pagination identical to PDF are not promised.

[HTML/CSS import](html-import-api.md) retains default semantic mode and offers explicit CSS-layout mode. Offline selector/media cascading, page/pagination rules, Flex/Grid, dimensions, and relative/absolute positioning map to a deterministic component tree; callers provide explicit fonts/resources. Layout leaves retain actual paragraphs and final external links/fields. Semantic outputs unable to express component layout return losses under ERROR/WARN/IGNORE and explicit handling. Scripts and implicit external access are not executed.

Default `ParagraphLayouter` uses JDK OpenType layout with explicit physical fonts for text requiring shaping, such as combining characters, Arabic, and Hebrew. Simple static-CFF text can retain native glyph mappings; complex shaping or explicit `layoutOpenType` uses outlines. Semantic paragraphs, rich-text cells, `FlowText`, headers/footers, footnotes, and contents text share this route. Simple text keeps existing metrics; use `OpenTypeText` to explicitly enable kerning/ligatures for purely Latin text.

Shaped results live in `TextLine.outlines()`, while the simple path uses `runs()`; these are mutually exclusive. When pagination/custom layout adjusts a baseline, use `atBaseline()` rather than copying only the old six fields. `minimumLineHeight(group, size)` returns a minimum line height compatible with both paths. Insufficient fixed line spacing fails explicitly, without automatically shrinking fonts. Glyph clusters crossing rich-text style boundaries are currently rejected; keep a combining sequence within one inline node.

Font groups still fail on missing glyphs by default; replacement mode preserves original character ranges and returns warnings. A single physical font must cover the whole glyph cluster; system fonts are not scanned.

`JUSTIFY` allocates gaps within soft-wrapped lines during layout. Optional `CJK_STRICT` checks source punctuation and nonbreaking combinations. Headings/lists support rich text and external links, with templates/DOCX preserving runs. See the [authoring guide](authoring-api.md) for common builders, automatic IDs, equal-width text tables, and atomic path output.

~~~java
var member = FontCollectionLoader.load(collectionBytes, 1); // TTC/OTC，明确选择第二个成员
var cff = TrueTypeFontLoader.load(otfBytes);                 // 静态 OTF/CFF 或 TTF
~~~

Collections and extracted members have separate byte budgets. [VerticalText (Chinese)](../vertical-text-api.md) retains its explicit character-cell entry point. The optional [native OpenType module (Chinese)](../native-opentype-api.md) provides HarfBuzz direction/feature shaping, variable glyf/CFF2, color glyphs, horizontal text within vertical text, and paginated vertical layout. Applications explicitly provide fonts and platform native classifiers. Static CFF body text supports native PDF font embedding; variable/color instances in the native module produce deterministic outlines/images and ActualText. Extraction, search, selection, and visual output are verified separately for both paths; logical anchor rectangles are not precise glyph outlines. Editable PDF fields still require explicit TrueType fonts.

`TableCell.rich(inlines, cellFormat)` retains actual font roles, colors, superscript/subscript, underline, and strikethrough. `InlineText(text, style, uri)` adds passive external links, permitting HTTP, HTTPS, and mailto while rejecting scripts, file links, and HTTP URLs containing user information. Links resolve against final line fragments, including paragraphs/tables spanning pages, without fetching targets. SVG/PNG still reject interactive objects; callers must explicitly supply a noninteractive version.

## Business templates

External text entry points provide a [safe XML template subset](xml-template-api.md) and [strict Markdown](markdown-template-api.md), compiled by separate adapters into existing nodes below. XML can declare fixed-width fields, level 1–9 decimal numbering, and passive text/image links; Markdown targets headings/paragraphs/single-level items/emphasis. Unknown content is explicitly rejected; resources are registered explicitly by callers. Arbitrary HTML/CSS is unsupported by these template entry points.

[XML multilevel numbering (Chinese)](../xml-numbering-api.md) reuses existing parent counters, restarts, and complete-number references. each/include preserve list identity and current-copy targets. Static levels are checked in every branch; actual parent integrity is verified during layout/export. [Phase 35 (Chinese)](../verification/phase-35-xml-numbering.md) verifies nine-level boundaries, native DOCX rules, and final PDF output. Later [phase 80 (Chinese)](../verification/phase-80-xml-semantic-saving.md) supports text links in numbered bodies; fields/images remain rejected.

XML [multiparagraph cells/nested tables (Chinese)](../xml-block-cells-api.md) map directly to the bounded recursive block model. Each/Rows preserve descendant formats, provenance, and same-copy references. Geometry, depth, and mutually exclusive content are checked in every branch at compilation; see [phase 28 (Chinese)](../verification/phase-28-xml-block-cells.md).

XML [themes/static names (Chinese)](../xml-themes-api.md) reuse complete body, six heading levels, and semantic-table defaults. Explicit `p`/`span` attributes override last, with compilation checks in every branch. Themes do not change XML body/cell configuration scopes or provide CSS; see [phase 31 (Chinese)](../verification/phase-31-xml-themes.md).

`DocumentTemplate(metadata, pageSettings, nodes, limits).render(data)` returns a complete semantic document, with no partial result on failure:

| Node | Behavior |
| --- | --- |
| `ValueBlock(prototype)` | Replaces variables such as `${customer.name}` in paragraphs, rich text, headings, lists, and semantic tables |
| `When(path, yes, no)` | Defaults to boolean TRUE and expands only the selected branch; overload `When(path, operator, value, yes, no)` supports bounded scalar comparisons, with nested else chains for first-match/other fallback; see [comparison conditions](xml-template-api.md#comparison-conditions-and-multiple-branches) |
| `Each(path, variable, children)` | Iterates lists with nested variable scope and deterministic iteration suffixes on block IDs |
| `Rows(id, path, variable, columns, headers, row, format)` | Fixed headers plus collection-driven body rows; empty collections fail explicitly, and `When` can control whether the table appears |

Data accepts only string-keyed Maps with nonnull values, Lists, strings, booleans, and standard finite numbers; arbitrary objects are not reflected. BigInteger/BigDecimal must be the exact standard classes. Snapshotting and expansion have depth, visit-count, and text budgets; expansion also has block/table-row budgets. Text budgets include Map keys, data strings, and generated strings. Visits include loop, cell, and inline work items. Budgets are checked before append and large-number conversion; even unreferenced oversized numbers fail. Missing paths, type errors, invalid expressions, unknown blocks, and limit failures have stable `BindingException.Code` values and safe paths; excessively long/invalid expressions point to `expression`.

Templates provide neither code execution nor implicit formatting. Callers prepare dates, money, and localized strings first. XML static reference targets relocate within current lexical-copy scope, retaining external static targets; references outside a loop do not infer an iteration. Dynamic target values supply the complete final ID without automatic prefixes/suffixes. Dynamic href values bind in every copy and validate the final URL; invalid protocols/credentials fail with redacted details. [Offline include (Chinese)](../xml-includes-api.md) selects only explicitly registered strings, supporting at most 16 acyclic levels, composed parent/child namespaces, and parent-to-child static references; see [phase 58 (Chinese)](../verification/phase-58-recursive-includes.md). Root static annotations use the complete binding entry point; component/dynamic annotation declarations remain rejected.

## Layout extensions

The four editable PDF field kinds use [FormStyle](form-styles-api.md) for text/mark color, fill, fixed/automatic borders, font size, and alignment. Explicit properties retain setting intent, old defaults remain compatible per field kind, and all AP states stay synchronized. Font size/alignment apply only to text/choice fields. See [phase 32 (Chinese)](../verification/phase-32-editable-form-styles.md); complete display of overly long field text and identical appearance rebuilding in arbitrary readers are not guaranteed.

`ColumnWidth.Auto(minPoints, maxPoints)` estimates preferred widths from actual cell text within explicit bounds, shrinking toward minimums when page space is insufficient while fraction columns share the remainder. Width includes padding; failure is explicit when no positive text width remains. Normal cell layout still produces final wrapping and warnings.

Ordinary merged text cells can cover Auto columns. Horizontal constraints distribute spare capacity in stable order; vertical owners participate once in preferred-width probing. [Inline nested-table Auto (Chinese)](../nested-automatic-tables-api.md) uses actual parent-cell width; Auto for tables containing block cells and automatic columns for single-pass sources remain separate. See the [merged automatic-column API (Chinese)](../automatic-merged-columns-api.md) and [phase 66 (Chinese)](../verification/phase-66-merged-automatic-columns.md).

`MultiColumn(child, columns, gap, true)` searches shorter column heights with at most 24 measurements without increasing the original page count. Its last fragment retains only actual height so subsequent body content can continue. Custom child components must be deterministic and repeatedly measurable. The original three-argument constructor retains sequential columns and whole-page height.

`ContinuousColumns(regionFlow, columns, gap)` begins in the current page's remaining height, using full column height on later pages. It supports `FlowText`/`OpenTypeText`, mixed `FlowColumn`, and `GridTable`. Equal-width text wraps only once per trial; variable-width minimum-line policies use bounded remeasurement. Images move atomically; headers repeat in each occupied column; merged-row groups stay whole by default. Subsequent content starts after the tallest column's actual height in the last fragment. `.balanced(true)` tries at most 24 layouts to shorten common column height while preserving page count and any skipped first page. For explicit merged-cell continuation, see the [continuation guide (Chinese)](../grid-continuation-api.md); basic geometry is in the [continuous-column API (Chinese)](../continuous-columns-api.md) and [mixed-column API (Chinese)](../mixed-columns-api.md).

`MultiFloatText(text, floats)` supports simultaneous avoidance of multiple left/right rectangles in its first fragment, staggered/stacked floats, skipping blocked line bands, and moving the group to the next page. Floats render once; continued body text resumes at full width. At most 64 actual nonoverlapping rectangles are supported; see [multiple-float wrapping (Chinese)](../multi-floats-api.md).

[ContourFloatText (Chinese)](../contour-floats-api.md) additionally supports arbitrary closed straight/cubic contours, source UTF-16 anchors, and future-region anchors. Complete line bands avoid actual contours; cross-page graphics use mask fragments, and semantic children genuinely continue through region flow. Atomic text components cannot continue by repeatedly clipping them; all work has finite budgets.

## Cancellation, timeouts, and file output

~~~java
var cancel = new AtomicBoolean();
var options = new ExecutionOptions(Duration.ofSeconds(30), cancel::get,
        progress -> showProgress(progress.stage(), progress.completed(), progress.total()),
        50L * 1024 * 1024);
engine.writeAtomically(document, backend, targetPath, options);
~~~

A single synchronous scope covers layout and output; total output is budgeted in bytes. `Progress` counts within each stage and is not an overall percentage. `total=-1` explicitly denotes an unknown total; check `hasKnownTotal()` before displaying a ratio. `ExecutionException` provides `CANCELLED`/`TIMEOUT`/`OUTPUT_LIMIT` and the last stage/block/page context. Thread interruption counts as cancellation and preserves the interrupted flag. The library creates no background execution threads; custom components, callbacks, and native calls observe cancellation only after returning or checking explicitly.

The stream entry point `engine.write(document, backend, stream, options)` preserves stream ownership; failure can leave partial bytes. `writeAtomically` requires an existing target parent and atomic-move support: it replaces the target only after successful temporary-file output, deleting the temporary file and preserving the original on failure. PDF `PdfOptions.storage(TEMP_FILE)` moves backend stream buffers to temporary files; Layout IR, Display List, and resources remain in memory, so this alone is not a complete streaming large-document engine.

Since `0.1.0-rc.2`, [ordinary-document page-by-page export](paged-document-api.md) is available: `engine.exportPaged` accepts `Document`, `PageDocument`, and `SectionedDocument`, plans final pagination, then paints/releases pages incrementally and returns a lightweight summary. Contents, future references, section page numbers, regions, and footnotes use final pagination. Comments/editable forms are rejected before opening the writer. With `PdfSpoolBackend`, completed pages' PDFBox objects are released and live page objects copied directly, avoiding per-page temporary PDF writing/reparsing. Complete input, the largest block, footnote slices, and finite indexes still consume memory; multipass planning adds computation. See [verification (Chinese)](../verification/paged-document-export.md). Earlier `0.1.0-rc.1` does not contain this entry point.

The same guide also provides on-demand ordinary block sources: `exportSemantic(PageSettings, BlockSource.Factory)` uses one layout pass when totals are known; `exportReplay` explicitly uses two stable-snapshot passes. Neither requires a complete body model first. Supported content includes headings/lists/captions, tables, images, components, external links, fixed regions, and final page fields. Global navigation, future references, sections, and footnote reflow are outside this source entry point. Sources/measurement caches release by current page/keep chain; global IDs and page summaries still grow with finite node/page counts.

Fixed-column plain/pure-rich-text long tables can use the separate [single-pass source API](streaming-table-api.md), measuring/writing synchronously per page and returning flat counts. [Phase 24 (Chinese)](../verification/phase-24-streaming-tables.md) verifies seven independent JVM groups: layout with discarded pages and actual PDF output at 1k/10k/100k rows, plus a 100k-row layout control with 64 MiB heap; all exit temporary-file counts/bytes are zero. [Phase 29 (Chinese)](../verification/phase-29-streaming-rich-text.md) adds pure rich text, actual font roles, and empty-run budgets, with nine plain/rich-text independent JVM groups including the 64 MiB layout control; the [guide (Chinese)](../streaming-rich-text-api.md) defines explicitly rejected semantics. Single-pass sources retain neither complete IR nor Display Lists and do not resolve future references. Use [explicit replay](streaming-replay-api.md) for future references, automatic widths, or unknown totals. The ordinary PDF backend still accumulates the page tree; optional `PdfSpoolBackend` uses a single-page working set and disk indexes. Each retains its own budgets/resource contracts.

Single-pass fixed-column horizontal spans were verified in [phase 64 (Chinese)](../verification/phase-64-streaming-column-spans.md): complete header/body coverage, measurement/presentation by actual physical columns, separate anchor/covered-slot counts, and preserved one-row lookahead/atomic-output protection. Images/passive links were verified in [phase 65 (Chinese)](../verification/phase-65-streaming-media.md); complete-line continuation is in [phase 67 (Chinese)](../verification/phase-67-streaming-row-split.md); actual page numbers/accurate totals are in the [streaming fields API (Chinese)](../streaming-fields-api.md). [Explicit bounded vertical spans (Chinese)](../streaming-row-spans-api.md) are now connected while retaining the default single-row path; they cannot combine with complete-line splitting.

Direct Display List output uses `backend.write(display, stream, options)`. Custom direct-layout workflows can run within `ExecutionContext.execute(options, operation)`, whose internal checkpoints share the same scope.

## DOCX and remaining scope

Existing PDFs use the separate entry points above. Original `read`/`copy`/`merge` still reject interaction and do not perform object remapping or semantic recovery; passive-object composition and model import require separate explicit choices. Layers/static tags are accepted only in explicitly enabled entry points according to the compatibility matrix. `copy`/`merge`/`composeObjects` still reject their new-page-tree remapping; signatures and unknown active structures remain rejected. ActualText, owner identity, and loss boundaries cannot be bypassed.

Strict DOCX round trips now support rich-text/inline-image cells and external hyperlink relationships. Links preserve semantics without accessing targets. See the [inline-image API](inline-images-api.md) for PNG/JPEG media, alternative text, and standard DrawingML scope. Automatic column widths round-trip through project extension properties; target Word widths need not visually match this engine's PDF results.

Semantic Table supports [column spans](column-spans-api.md), [row spans](row-spans-api.md), and [bounded recursive block cells/nested tables (Chinese)](../block-cells-api.md). DOCX reads/writes standard gridSpan/vMerge and p/tbl/p; deep Java binding preserves descendant IDs and hierarchical provenance. Vertical connected groups paginate atomically by default; explicit row splitting supports recursive cells/vertical-owner continuation without duplicated content in covered rows. Invalid spans, complete parent chains, coverage, and continuation intervals fail. Allowing loss does not infer geometry or drop nonempty continuation cells; empty continuation cells still validate styles/hidden semantics. Multiparagraph cells retain separate Paragraphs and actual empty trailing paragraphs; owned structural trailing paragraphs/bookmark owners must validate. Other unsupported structures fail under STRICT and return diagnostics under ALLOW_LOSS. This is not full OOXML Schema validation; see [phase 57 (Chinese)](../verification/phase-57-recursive-tables.md) for recursive continuation/vertical-group splitting. [Phase 103 (Chinese)](../verification/phase-103-native-docx-semantic-editing.md) verifies actual Word editing/saving/reimport, native pages, and PDFs for four-level combined tables, page regions, and floating objects; arbitrary Word-file compatibility does not follow from this subset.

Native PAGE/NUMPAGES/PAGEREF/numbered REF work in body text and ordinary cells, with explicit widths and flat complex-field import. Local Word 16.0 was tested updating/exporting example PDFs. Repeated-header PAGE, non-block-start page-number bookmarks, annotation markers, and caption numbering remain limited; see the [DOCX fields API (Chinese)](../docx-fields-api.md) and [phase 12 verification (Chinese)](../verification/phase-12-docx-fields.md).

## Semantic streaming, explicit replay, and disk-indexed PDF

[Semantic long tables/replay](streaming-replay-api.md) provide single-pass recursive block cells, nesting, and vertical-owner continuation.
