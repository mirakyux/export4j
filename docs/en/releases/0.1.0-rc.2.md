# Export4j 0.1.0-rc.2

This candidate adds shorter common API entry points, page-at-a-time export for ordinary documents, and on-demand block sources, while reducing duplicate resources in complete layout and PDF writing. Java remains at 21; 16 libraries and the BOM share one version. The optional designer is outside Maven publication.

## Main changes

- Common output methods accept `Path`, `File`, local path strings, and borrowed `OutputStream`s. Conveniences cover font combinations, image dimensions, page units, row sources, and document conversion. HTML/Markdown string content and file paths still use explicitly different methods.
- `DocumentEngine.exportPaged` delivers layout/painting one page at a time and returns a lightweight summary. `exportSemantic`/`exportReplay` use on-demand `BlockSource`s, providing single-pass export with exact total page counts and explicit replay of stable sources respectively.
- Bounded reuse of equal model styles, cells, and table geometry reduces duplicate string validation, font programs, and drawing resources. The paged PDF backend additionally reuses font subsets, images, and a disk index.
- Ordinary PDF saving disables object-stream packing to reduce additional whole-graph indexing during save. Content, font, and image streams retain their existing compression.

## Compatibility and known limits

- Existing complete-layout/export entry points still return complete Layout IR/Display Lists, with memory growing with input and page count. To reduce large-document working sets, explicitly choose paged, block-source, or long-table row-source entry points and configure finite budgets appropriate to input scale.
- In this batch's complex 10,000-page sample, a forward-only block source plus `PdfSpoolBackend` succeeded three times with a 128 MiB Java heap. Complete-model/complete-layout export with the ordinary backend succeeded three times at 512 MiB, with limited headroom. The complete-model path still ran out of memory at 128 MiB. These samples do not guarantee arbitrary content, page counts, or heap configurations.
- Disabling object streams can enlarge PDFs. The ordinary 10,000-page sample grew from approximately 34.56 MiB to 43.57 MiB, about 26.1%. Size depends on content; that percentage is not a fixed cost.
- `PdfSpoolBackend` produces ordinary PDFs and does not extend PDF/A, PDF/UA, encryption, or signing support. Paged entry points explicitly reject unsupported interactions/source declarations. Editable forms continue to use the corresponding complete entry points.
- Path output still atomically replaces within the same directory, preserving the old target on failure. Streams remain caller-owned and can contain partial bytes after failure. Replay requires the same business snapshot and deterministic components, without implicitly requerying dynamic data.
- Public APIs remain at release-candidate status. JVM signature comparison against the reviewed candidate baseline found no incompatibilities in this batch; it does not prove all behavioral/visual results are unchanged.

## Pre-release verification

The local Windows/Java 21 batch completed the repository build, local Maven bundle, and isolated-consumer verification with 2,347 Java tests and no failures, errors, or skips. Independent structure checks, Poppler/PDFium rendering, and visual sampling covered affected outputs. Capacity checks included large tables, multiple fonts, distinct transparent images, repeated/concurrent calls, cancellation, and budget failure. Archive samples passed veraPDF PDF/A-2b checks.

These are local pre-release results. The formal RC2 workflow rebuilds, signs, audits dependencies, checks BOM/SBOM, verifies signature tamper rejection, and uses isolated consumers before and after upload. Remote CI and publication status follow their corresponding Actions runs.
